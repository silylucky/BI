# 样例

## 例 1：看起来像空指针，实则面级错误处理

**现象**：订单详情偶发白屏；控制台 `Cannot read property 'amount' of null`。

**取证**：失败请求返回 `data: null` 且 HTTP 200；列表页同 API 在无权限时也是 200+null。

| 项 | 结论 |
|----|------|
| 主层 | **架构/缝**（错误与空态未在 API 信封统一）次层：代码未判空 |
| 点 | 详情页对 null 崩溃 |
| 线 | 所有消费该信封的详情/编辑页 |
| 面 | 多处 BFF `return null` 表示业务失败 |

**错误修法**：只在详情页加 `?.`。  
**推荐**：缓解可加可选链；正式策略=统一信封（code/message/data）+ 线上面改消费方；可交接 code-reviewer「API 信封」族。

**用户选项**：缓解+点护栏 / 修线（本域消费方）/ 面（信封标准化回流）。

## 例 2：语法/机械，可点修

**现象**：导出 CSV 文件名乱码，仅 Windows Excel。

**根因**：未加 BOM；主层=**语法/机械**（格式约定）。

| 粒度 | 结论 |
|------|------|
| 点 | 导出函数加 UTF-8 BOM |
| 线 | 仅此一处导出 |
| 面 | rg 无第二处 CSV 导出 |
| 发散 | 参数轴 N/A；函数轴无兄弟导出；页面轴仅设置页一处 |

**推荐**：决策卡问用户 → 选「只修点」则本会话改；无需 go-fast。

## 例 2b：换页面还会炸（发散命中 → go-fast）

**现象**：用户管理「编辑」保存后金额字段变 0；创建页正常。

**根因**：编辑页提交把未挂载的受控输入当成 `0`；主层=**代码/实现**。

| 轴 | 结论 |
|----|------|
| 页面 | 角色编辑、租户编辑同 composable `useEntityForm` 同样写法 → 仍会炸 |
| 函数 | `normalizePayload` 被 4 个编辑页共用 |
| 参数 | 其他 number 字段同样风险 |

**错误结案**：只改用户管理编辑页。  
**推荐**：决策卡列 4 页候选 → 询问 → 用户选「3 面+发散」→ **go-fast** 路径 B：`docs/specs/bugfix-entity-form-zero.md` + 按页分票或先修 helper 再扫消费方。

## 例 3：流程规则冲突

**现象**：已驳回单据仍可「再次提交」；部分角色说这是 bug，运营说要支持。

**主层**：**流程/产品规则**（状态机未钉死）。

**动作**：不改码；grilling/问用户钉规则 → 再改状态机与按钮显隐（线=所有入口）。  
误判为代码漏 `if` 会修错业务。

## 例 4：代码逻辑 + 可批量面

**现象**：创建资源超时 30s 失败；重试第二次成功但生成两条记录。

**主层**：**代码/实现** 偏 **架构**（缺幂等）— 主层标 **架构/缝**（写路径无幂等键）。

| 粒度 | 结论 |
|------|------|
| 点 | 创建 API 无 Idempotency-Key / 唯一约束 |
| 线 | 所有「创建类」写路径 |
| 面 | ast-grep 找无唯一约束的 create |

**推荐**：禁止只加「前端防抖」。策略=缓解（先关自动重试）+ 回流（幂等键+DB 唯一）+ 面清单分批。  
决策选项默认：**缓解 + 回流**。

## 例 5：决策卡缩略

```markdown
# Bug 决策卡
## 现象
- 期望：保存草稿成功提示
- 实际：提示成功但刷新后丢失
- 复现：编辑页 → 存草稿 → 刷新；必现；Chrome
- 证据：PUT /drafts 204；GET 仍旧数据；无错误日志

## 根因
- 一句话：保存打到只读副本地址，主库未写
- 主层：架构/缝
- 依据：读写分离路由把 PUT 指到 replica

## 点线面
| 点 | 草稿 PUT 路由错误 |
| 线 | 所有写动词是否误走读库 |
| 面 | 网关/ORM 读写策略；候选写接口 ~12；手法一致可批量核查 |

## 我的推荐
> **推荐：选项 4 — 先配置层强制写走 primary 止血，再排「网关写动词统一路由」正式切片**

| 维度 | 表现 | 依据 |
|---|---|---|
| 架构与边界 | 根因在读写分离这道缝上；正式修必须收在网关，逐个接口改 = 固化假缝 | 主层=架构/缝 |
| 长期维护 | 缝上统一后新增写接口自动正确；点修则每加一个写接口再赌一次 | 候选写接口 ~12，仍在增长 |
| 可靠性 | 静默丢数据、无错误日志，属最坏一类；止血须小时级 | PUT 返回 204 却未落库 |
| 爆炸半径与回滚 | 缓解是配置项，秒级回滚；网关路由改动触及全部写路径，需灰度 | — |
| 成本与时效 | 网关统一要 ADR + 灰度，拖不起阻断期 | — |
| 验证可行性 | 缓解后原复现即可验；正式项按 12 个写接口抽检 | — |

**为何不是别的**：选 1 只修草稿这一条路由，其余 11 个写接口继续静默丢数据；选 3 现在就动网关，
在数据正在丢的时段做大范围路由改动、回滚代价太高；选 5 不可接受，这是数据正确性问题。

**代价与置信度**：缓解期内配置与代码两处真相并存，必须挂号并设撤出条件；置信度**中**——
12 个写接口里有 3 个走自定义 DAO，尚未确认是否复用同一路由策略。

- 请确认：④缓解+回流（推荐） / ③立即全面统一 / ②仅核查写动词线
```
