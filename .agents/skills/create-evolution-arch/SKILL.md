# Create Evolution Arch（人工交互）

## 何时使用

- 用户手动触发：为目标项目首次生成 `docs/arch.md`、体检已有架构文档，或修订已经过时的架构决策
- 项目需要把 PRD/goal 中的产品事实落到技术架构、部署边界、模块边界、请求路径与关键约束
- 需要用某个参考 `arch.md` 学习章节结构时：只参考结构、表达层次和覆盖面，**不得复制参考项目的技术事实**
- **禁止**被无人值守演化流程（Automations / evolution-* subagent）调用

## 生产姿态（全程强制）

`docs/arch.md` 描述的是**可上线生产系统**如何组成与演进，不是演示拓扑。

| 禁止出现在 arch 中的内容 | 正确做法 |
|--------------------------|----------|
| stub / mock 假服务 / 内存假后端作为正式组件 | 只画真实进程、真实外部依赖；测试双不进架构图 |
| 「临时 mock，上线前替换」作为架构决策 | 决策要么接真实集成，要么能力未就绪则不宣称、不挂生产入口 |
| MVP / demo 部署形态当目标态 | 可用「首版部署范围更小」，但组件与路径必须是生产级真实实现 |
| 假绿友好路径（永远成功的占位适配器） | 失败模式、降级、熔断须诚实；禁止「占位成功」 |

**例外（勿写入正式架构组件）**：`*_test` / fixture / 仅本地测试 harness 中的 mock —— 可在「测试策略」一笔带过，**不得**出现在系统架构图、请求路径、模块边界表里。

## 文档定位

`docs/arch.md` 是自我演化的**技术架构与关键决策源**，回答「系统如何组成、为何这样设计、哪些边界不能跨、如何部署和演进」。它不替代 PRD，不新增产品需求，不排里程碑。

| 文档 | 定位 | 本 skill 是否修改 |
|------|------|------------------|
| `docs/automate/goal.md` | 产品方向与边界 | 否，只读 |
| `docs/automate/prd.md` + `docs/automate/prd/*.md` | 功能真理源与验收标准 | 否，只读 |
| `docs/automate/plan.md` | 人工里程碑与顺序干预 | 否，只读 |
| `docs/automate/evolution-state.md` | 当前轮次、待办池、模块地图、项目 skill/rule 索引 | 否，只读 |
| `docs/arch.md` | 技术架构、部署形态、模块边界、关键决策 | 是 |

## 工作模式

| 模式 | 触发 | 输出 |
|------|------|------|
| 新建 | `docs/arch.md` 不存在 | 完整架构文档 |
| 体检 | `docs/arch.md` 已存在，用户要求检查 | 质量评分 + 漂移清单 + 修订建议 |
| 修订 | 用户确认要调整已有架构章节 | 最小范围修改 + 决策记录 |
| 迁移 | 架构内容散落在 README、PRD、设计文档 | 汇总到 `docs/arch.md`，源文档只在用户确认时改引用 |

## 硬确认门（强制 · 一次一问）

在**分析 / 敲定技术栈与部署形态**阶段，下列主题**必须逐项询问**，给出选项 + **推荐项**，等用户**明确选择或确认**后，方可写入对应章节。禁止静默采用默认、禁止跳过整门只标「以后再说」却写成已定目标态。

| 顺序 | 主题 | 写入章节 | 推荐（政企/私有化 Web 常见） | 选项示例 |
|------|------|----------|------------------------------|----------|
| H1 | **技术栈总览** | §2 | 先扫仓推断，再请用户确认「已落地 / 目标态」 | 确认推断 / 修正某层 / 标待定 |
| H2 | **多数据库** | §2 · §7 | 强制可切换：**SQLite** + **MySQL（含 TiDB 兼容）** + **PostgreSQL** | 三者皆要（推荐）/ 仅子集（须说明）/ 待定 |
| H3 | **高可用** | §3 · §4 · §10 | 架构显式支持**单机**与 **HA（多实例）**，配置切换 | 单机+HA 皆要（推荐）/ 仅单机（arch 标明）/ 待定 |
| H4 | **国密为默认密码学** | §2 · §9 · 必要时 §11/ADR | 业务加解密/签名/摘要默认 **SM4/SM3/SM2** | 国密默认（推荐）/ 国际算法为主（须 ADR 理由）/ 混合（列边界） |
| H5 | **可观测性** | §10 | 日志（滚动）+ **指标（RED 等）** + **链路（request/trace id）** + 告警归属 | 日志+指标+链路（推荐）/ 仅日志（弱，须确认）/ 待定范围 |
| H6 | **外部依赖与集成契约** | §8 | 逐个依赖：协议、认证、超时/重试、失败语义、数据归属；无则确认「无」 | 按清单确认 / 补充依赖 / 确认无外部依赖 |
| H7 | **数据目录与种子** | §7 · §3 | **能力**必有：migrations + 幂等 seed + 表定义真源；路径**按栈**（见下）；默认管理员可 `admin`/`admin` 但**强制改密** | 采用栈推荐路径（推荐）/ 自定义路径 / 待定 |

### H7 说明（合理且须按栈裁剪）

「要有 migrations / seed / 表定义」作为**能力**是合理的；**目录名不要写死 `db/`**。

| 能力 | 要求 |
|------|------|
| migrations | 版本化、可顺序重放 |
| seed | 平台幂等种子；**demo 种子可选且默认不进生产启动** |
| 表定义 | DDL / ORM schema / prisma 等真源或生成入口 |
| bootstrap 管理员 | 允许首装弱口令（如 admin/admin）；**首次登录或启动检测强制改密**；生产禁长期弱口令 |

路径推荐（询问时按 H1 已确认栈选用；细则可链 create-project-rules `references/db-layout.md`）：

| 栈 | 常见布局 |
|----|----------|
| go-zero | `db/migrations` · `db/seed` · `db/ddl`+`db/model` |
| GoFrame | 按仓惯例 / manifest·resource |
| FastAPI | `alembic/` + `app/seed` 或 scripts |
| Flask | `migrations/` + seed 脚本 |
| Prisma | `prisma/migrations` · `prisma/seed` · `schema.prisma` |
| Django | `<app>/migrations` + fixtures/commands |

### 执行规则

1. **先扫仓再问**：用 README、goal、依赖清单、配置推断推荐，问题里写清「根据仓库推断：…；推荐：…」
2. **一次只问一门**（H1→H7 顺序可微调；H2–H7 不得整批跳过）。**H7 在 H1、H2 之后问**（先有栈与多库，再定目录）
3. 用户选择后，在会话中维护 **Hard Confirm Card**（见下）；写入 arch 前再展示全卡请用户做**总确认**
4. 用户拒绝推荐 → 按选择写；若削弱生产能力（如不要 HA、不要多库、不要指标、不要迁移）→ 写入时标明范围与风险，**不得**假装仍是完整生产目标态
5. 国密选「国际算法为主」→ 必须追问是否开 ADR；无理由则标 `（待确认）`，不写成已定合规默认
6. MySQL 项须点名：**是否含 TiDB 协议兼容目标**，写入 §7
7. §8 每个外部依赖确认失败语义时：若用户说「失败也返回成功」→ **拒绝**写入
8. H7：禁止不分栈强行所有项目都用 `db/`；禁止 demo 种子默认打进生产启动；禁止生产永久 `admin`/`admin` 且不强制改密

### Hard Confirm Card（写入前必展示）

```markdown
## Hard Confirm Card（用户已选）

| 门 | 选择 | 写入位置 |
|----|------|----------|
| H1 技术栈 | … | §2 |
| H2 多数据库 | sqlite / mysql(+TiDB?) / postgres … | §2 §7 |
| H3 高可用 | 单机 / HA / 二者 … | §3 §4 §10 |
| H4 国密默认 | 是 / 否 / 混合 … | §2 §9 |
| H5 可观测性 | 日志±指标±链路 … | §10 |
| H6 外部契约 | 依赖列表或「无」… | §8 |
| H7 数据目录与种子 | 路径… · admin 强制改密：是/否 | §7 |

总确认：请回复「确认写入」或指出要改的门。
```

## 提问纪律

- **一次只问一个问题**；能给选项就给选项（多选一优先，附推荐项）
- 提问前先读上下文：README、`docs/automate/goal.md`、`docs/automate/prd.md`、已有 `docs/arch.md`、关键配置文件、`git log -10`
- 用户提供参考架构文档时，先提炼其章节骨架，再结合目标项目事实重写
- 用户跳过**非硬确认门**问题 → 采用推荐默认值，并在产出中该处标注 `（待确认）`
- **硬确认门（H1–H7）**：跳过 ≠ 默认写入为「已完备」；须停问或写入缩小后的明确范围，并在 Card 留痕
- 写入前必须展示「Hard Confirm Card + 变更摘要 + 将写入的章节预览 + 仍待确认项」，等待用户明确确认
- 发现用户想用 stub/mock「先跑通」→ **拒绝写入架构**，改为讨论真实依赖接入或缩小 In Scope
- **模块/边界称呼当场钉死**：与 goal/prd 冲突时点名问清；§6 模块表只用规范名
- **用户口述「系统如何工作」须对账代码**：矛盾写入待确认或已知债务，禁止把口述当目标态
- **§11 决策稀疏**：仅当「难回退 + 无上下文会惊讶 + 真有取舍」三者皆真时写入关键决策；易改选型一笔带过。确认后若值得独立留痕，可另写短篇 `docs/adr/<主题>-<模块>.md` 并在 §11 链过去——**不要**每条选型都开 ADR
- 与仓内 **create-project-rules** 红线对齐时：arch 中的国密/多库/HA/观测/外部契约/数据目录表述应可被后续 rules 消费，但**不得**未询问就替用户选定

## 质量评分（100 分）

| 维度 | 分值 | 检查点 |
|------|-----:|--------|
| 架构定位清晰度 | 10 | 能说明系统形态、核心用户、部署环境、与 goal/prd 的关系 |
| 技术栈完整性 | 10 | 后端、前端、数据、缓存、队列、存储、协议、构建部署均有明确选型；**含用户已确认的多库/国密姿态** |
| 边界与模块划分 | 12 | 模块职责、进程边界、外部系统、禁止跨界点清楚 |
| 请求与数据路径 | 12 | 关键用户/API/后台任务/异步链路可追踪，且每跳为真实组件 |
| 部署与运维可落地 | 12 | 环境、配置、依赖、扩缩容、备份、**HA 单机切换**、失败模式有说明 |
| 可观测性完备度 | 8 | 日志 + 指标 + 链路（或用户确认的缩小范围）写清；非仅「有日志」 |
| 外部契约完备度 | 8 | §8 依赖方/协议/认证/超时重试/失败语义/数据归属；或明确「无」 |
| 生产诚实性 | 13 | 无 stub/假服务/假绿路径；外部依赖失败行为诚实；无 MVP 玩具拓扑 |
| 决策可追溯性 | 7 | 关键取舍有原因、状态、影响范围；国密例外有 ADR 或待确认 |
| 安全与合规覆盖 | 8 | 认证、权限、审计、密钥、**国密默认或例外**、数据保护与 PRD/goal 对齐 |

评分解释：

| 分数 | 结论 |
|------|------|
| 90-100 | 可作为 P1/P3 架构约束与设计评审稳定输入 |
| 80-89 | 可用，但有少量待确认或薄弱链路 |
| 70-79 | 能启动，但容易让实现阶段在边界/部署/数据路径上漂移 |
| <70 | 建议继续交互澄清，不写入正式 arch 或只写草案 |

**硬门槛**：

- 架构图或请求路径含正式 stub/mock 假服务，或把 demo 拓扑当目标态 → 「生产诚实性」0 分，总分上限 69
- **H2–H7 任一未询问、未获用户选择却写成已定完备目标态** → 相关维度扣至不及格，总分上限 79，并在 followups 列出未确认门

## 首次生成（arch.md 不存在）

1. 读项目事实源：
   - `README.md`
   - `docs/automate/goal.md`
   - `docs/automate/prd.md` 与必要分片
   - `docs/automate/evolution-state.md` 的模块地图（若存在）
   - 关键清单与配置：`package.json`、`go.mod`、`pyproject.toml`、`Cargo.toml`、`Makefile`、`docker-compose*`、`Dockerfile`、`etc/`、`.cursor/rules/`、`.agents/skills/` 等按项目实际存在选择
2. 若用户提供参考 `arch.md`：
   - 只抽取章节结构、覆盖面、元信息写法、图表层次
   - 明确过滤参考项目的名称、技术栈、进程、路由、PRD ID、规则路径、部署事实
3. **跑硬确认门 H1–H7**（一次一问，扫仓推断 + 推荐 + 用户选择），维护 Hard Confirm Card
4. 继续确认其他核心点（可与 H 门穿插，但 H 门不得省略）：
   - 系统定位与**生产**部署形态
   - 进程/服务/模块边界
   - 请求路径与数据路径
   - 配置、存储、队列、缓存（与 H7 数据目录衔接）
   - 安全（认证/RBAC/审计，与 H4 国密衔接）、演进路线
5. 可做有界代码扫描补架构事实：
   - 优先读入口、配置、路由、模块目录，不做全仓逐文件阅读
   - 若扫到非测试 stub/mock/假成功 → 记入「待清除债务」，**不得**合理化进目标架构
   - 发现不确定事实时标 `（待确认）`，不得臆造
6. 写入前展示 **Hard Confirm Card + 完整章节预览**，用户确认后写入 `docs/arch.md`

## 重复执行（arch.md 已存在）

1. 读现有 `docs/arch.md`，对照 README、PRD、代码入口、配置和最近提交
2. 按「质量评分」给出现状分数、扣分原因、漂移风险
3. **体检硬确认门覆盖**：国密默认、多库（sqlite/mysql·TiDB/postgres）、HA、可观测性、§8 外部契约、**§7 迁移/种子/表定义路径与强制改密**；缺则列入修订候选并**一次一门**回问
4. 列出其他疑似问题：
   - 技术栈与依赖文件不一致
   - 架构图缺少新模块或仍保留已删除模块
   - 请求路径、配置路径、部署进程与代码现状冲突
   - 安全/权限/审计要求与 PRD 或 goal 不一致
   - 关键决策没有原因、状态或影响范围
   - **正式组件/路径中出现 stub、mock、假服务、demo 拓扑、MVP 措辞**
5. 逐条向用户确认修订（一次一条）
6. 汇总修订摘要与章节预览，用户确认后最小修改
7. 修订后更新元信息中的 `last_updated`，必要时追加「关键决策记录」条目

## 推荐产出结构

节标题可按项目调整，但首次生成默认使用：

````markdown
# <项目名> — 架构文档

```yaml
version: 0.1.0
last_updated: YYYY-MM-DD
status: draft | planned | active
goal_ref: docs/automate/goal.md
prd_ref: docs/automate/prd.md
rules_ref: <按项目实际填写或 none>
posture: production   # 禁止 demo/mvp 作为 status 替代
crypto_default: sm   # sm | international | mixed（须与用户确认一致）
ha_modes: [single, ha]  # 用户确认的部署形态
db_drivers: [sqlite, mysql, postgres]  # mysql 含 TiDB 兼容时在正文说明
```

> 本文档记录技术架构与关键决策，不替代 docs/automate/prd.md 的功能真理源。
> 约束：正式路径禁止 stub/mock 假服务与假绿；测试双不进入架构图。

## 1. 定位
## 2. 技术栈
## 3. 发布与部署策略
## 4. 系统架构
## 5. 请求路径
## 6. 模块边界
## 7. 数据、存储与配置
## 8. 外部依赖与集成契约
## 9. 安全、权限与审计
## 10. 可观测性与运维
## 11. 架构决策记录
## 12. 演进路线与待确认项
## 13. 已知债务（若有 stub/假绿，仅登记清除计划，不得标为目标态）
````

「## 2. 技术栈」须含：后端/前端/协议，以及用户确认的 **db_drivers**、**crypto_default（国密）**。

「## 7. 数据、存储与配置」须写清：sqlite / mysql（是否 TiDB 兼容）/ postgres 如何切换；**migrations / seed / 表定义**的**实际路径**（按栈，非盲抄 db/）；平台种子 vs demo 种子；默认管理员与**强制改密**；配置哪些进库热改（若有管理面）。

「## 8. 外部依赖与集成契约」至少写清：依赖方、协议、认证、超时/重试、失败语义、数据归属。无外部依赖则写「无」并说明理由（用户已确认）。

「## 9」须写明国密默认或例外边界（与 H4 一致）。

「## 10」须按 H5 写日志/指标/链路/告警，禁止用「有日志」代替指标与链路（除非用户明确缩小范围）。

「## 3 / 4」须按 H3 写单机与 HA。

「## 13. 已知债务」仅当代码里已存在非测试 stub/假绿时使用：登记位置 + 清除条件；**禁止**把债务写成推荐架构。

## 交互式引导问题库

按需使用，一次只问一个。**硬确认门优先用下列 H 行**，其余按需：

| 场景 | 问题 |
|------|------|
| **H1 技术栈** | “根据仓库推断技术栈是 …，是否确认作为目标态？需要改哪一层？（已落地 / 目标态 / 待定）” |
| **H2 多数据库** | “是否要求同时支持 SQLite、MySQL（含 TiDB 兼容）、PostgreSQL，并可通过配置切换？推荐：三者皆要。” |
| **H3 高可用** | “部署是否需要同时支持单机与高可用（多实例）配置切换？推荐：二者皆要并写清锁/会话/共享存储。” |
| **H4 国密** | “业务侧加解密/签名/摘要是否以国密（SM4/SM3/SM2）为默认？推荐：是。若否，是否接受单独 ADR？” |
| **H5 可观测性** | “可观测性范围选：①日志+指标+链路（推荐）②仅日志 ③自定义？告警归属写在哪份文档？” |
| **H6 外部契约** | “外部依赖清单是 …（或无）。请逐个确认：不可用时失败/重试/降级？是否禁止假成功？” |
| **H7 数据目录** | “按当前栈推荐布局是 …（migrations/seed/表定义）。是否采用？默认管理员是否 admin/admin 且首次强制改密？demo 种子是否默认不进生产启动？” |
| 定位不清 | “这个系统更像模块化单体，还是多进程/多服务生产系统？首版范围可以小，但组件是否全部按生产真实依赖设计？” |
| 技术栈待定 | “这项技术是已经在代码里落地，还是目标态选择？是否准备用 mock 顶替真实依赖？”（后者 → 拒绝） |
| 部署边界 | “首版部署实例数可以少，但单实例是否仍按生产配置、观测、密钥与失败模式设计？” |
| 模块边界 | “这个能力应该归入现有模块，还是作为独立边界记录？有没有占位适配器被误当成正式模块？” |
| 请求路径 | “用户触发后，端到端每一跳的真实组件是什么？哪一跳目前是 stub？”（有 stub → 标债务或缩小宣称） |
| 数据归属 | “这类数据的真理源是数据库、对象存储、外部系统，还是配置文件？” |
| 集成契约 | “该外部依赖不可用时，系统应失败、重试还是降级？降级是否仍返回‘成功’假绿？”（假绿 → 禁止） |
| 安全约束 | “这里需要权限、审计、密钥保护、还是合规留痕？” |
| 决策取舍 | “这个选型主要为了可维护性、性能、私有化部署、还是团队熟悉度？（交付速度不能成为引入假服务的理由）” |
| 是否值得 ADR | “换掉它是否成本高、后人是否会惊讶、当时是否有真实备选？三者缺一 → 只留 §11 一行或不记。” |
| 称呼冲突 | “架构图里的模块名与 PRD 域/功能称呼是否同一事物？采用哪个规范名？” |

## 红线

- 写入前必须展示预览并获得用户确认
- **必须**完成硬确认门 H1–H7 的询问与用户选择（或明确缩小范围），禁止未问就写成完备目标态
- **禁止**不分技术栈强行所有项目使用同一 `db/` 路径名；路径须与 H1 栈及用户确认一致
- **禁止**把参考 `arch.md` 的项目事实复制到当前项目
- **禁止**在 `docs/arch.md` 新增未经用户确认的产品需求；需求事实应进入 PRD
- **禁止**改 `goal.md`、`prd.md`、`plan.md`；发现不一致只提示对应 skill 处理
- **禁止**演化流程调用本 skill
- **禁止**将 stub / mock 假服务 / 假绿路径 / MVP·demo 拓扑写为目标架构或正式请求路径
- **禁止**为每个小库/小配置开 ADR；不过「难回退 × 会惊讶 × 真取舍」门槛就不提议独立 ADR
- **禁止**把易过期的具体文件路径堆进「关键决策」（路径属实现快照；决策写取舍与约束）
- 不确定的架构事实必须标注 `（待确认）`，不得臆造
- 代码中已有假实现 → 只能进「已知债务」并推动清除，不得合理化
