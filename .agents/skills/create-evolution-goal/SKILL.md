# Create Evolution Goal（人工交互）

## 何时使用

- 用户手动触发：为目标项目首次生成 goal.md、体检已有 goal.md，或修订已过时 / 反推错向的 goal.md
- 本 skill 是 goal.md **唯一合法修改通道**；演化 subagent 禁止修改已存在的 goal.md（缺失时 doc-bootstrap 仍可首次生成）
- **禁止**被无人值守演化流程（Automations / evolution-* subagent）调用

## 生产姿态（全程强制）

本 skill 服务**大型生产项目**的方向锚定，不是原型验证或演示稿。

| 禁止写入 goal 的表述 | 正确替代 |
|----------------------|----------|
| MVP / demo / 玩具 / 先能跑再说 | 首版即生产可用边界；范围用 In/Out of Scope 收缩，不降交付标准 |
| 「能演示即可」「有界面就算达成」 | 可观测、可判定的生产成功指标（可靠性、正确性、可运维、合规） |
| 「后续再补真实现 / 先 mock」 | Out of Scope 明确排除假服务；实现路径只能是真实依赖 |

若用户主动提出 MVP/demo 目标：一次说明冲突，引导改写为「生产首版范围更小，但每条目标可真实验收」；**不得**把 MVP/demo 写进正式 `goal.md`。

## 文档定位

`docs/automate/goal.md` 是自我演化的**方向与边界源**，回答「为什么做、给谁做、做到什么程度、不做什么」。它不列具体功能清单，不替代 PRD，不排里程碑。

| 文档 | 定位 | 本 skill 是否修改 |
|------|------|------------------|
| `goal.md` | 产品定位、终极目标、边界、成功指标 | 是 |
| `prd.md` + `prd/*.md` | 功能真理源、验收标准、8 维评分、依赖性评分、goal_ref 映射 | 否，修订后提示体检 |
| `plan.md` | 人工里程碑与顺序干预 | 否 |
| `evolution-state.md` | 当前轮次、待办池、模块地图、Token 索引、STUCK 计数 | 否 |

## 工作模式

| 模式 | 触发 | 输出 |
|------|------|------|
| 新建 | `goal.md` 不存在 | 完整 `goal.md` |
| 体检 | `goal.md` 已存在，用户要求检查 | 质量评分 + 问题清单 + 修订建议，不默认写入 |
| 修订 | 用户确认要改已有内容 | 逐条确认后的最小修改 |

## 提问纪律（苏格拉底式）

- **一次只问一个问题**；能给选项就给选项（多选一优先，附推荐项）
- 提问前先读上下文：README、package 描述、docs/、`git log -10`、已有 goal.md
- 用户跳过问题 → 采用推荐默认值，并在产出中该处标注 `（待确认）`
- 写入前必须展示「变更摘要 + 将写入的章节预览」，等待用户明确确认
- 若用户用词含 MVP / demo / stub / mock / 假数据冒充交付 → **当场纠正**，再继续提问
- **锐化过载词**：用户说「用户 / 账号 / 租户 / 平台」含混时，当场钉死规范称呼并写入产品定义（勿另起独立术语文件；goal 正文即口径）
- **边界模糊时给一个具体场景**：用「若发生 X，算 In 还是 Out？」逼清边界，再写 Out of Scope；禁止只堆抽象名词

## 质量评分（100 分）

| 维度 | 分值 | 检查点 |
|------|-----:|--------|
| 定位清晰度 | 15 | 一句话说明用户、场景、问题、产品形态；隐含生产系统而非演示品 |
| 目标可追踪性 | 15 | 终极目标 3–6 条，编号稳定，可被 `goal_ref` 引用 |
| 边界明确度 | 20 | In Scope / Out of Scope 可阻止无关演化；Out 含假服务/半成品交付 |
| 成功指标可判定性 | 20 | 指标可被 agent 或测试判断；方向性指标显式标注；禁止「能演示」类指标 |
| 生产就绪姿态 | 15 | 无 MVP/demo/玩具措辞；目标暗示真实集成、可运维、可审计，而非占位 |
| PRD 衔接度 | 10 | 目标编号适合映射到功能项 |
| 文档可维护性 | 5 | 章节固定、低频人工修订、无实现细节堆积 |

评分解释：

| 分数 | 结论 |
|------|------|
| 90-100 | 可作为自动演化稳定锚点 |
| 80-89 | 可用，但有模糊项需后续确认 |
| 70-79 | 勉强可用，容易导致选题漂移 |
| <70 | 建议先继续交互澄清，不写入正式 goal |

**硬门槛**：出现 MVP/demo 作为正式目标，或成功指标仅「可演示」→ 该项维度 0 分，总分上限 69，不得标为正式可用。

## 首次生成（goal.md 不存在）

按顺序逐项探讨，每项一轮提问：

| 节 | 探讨内容 |
|----|----------|
| 1. 产品定义 | 一句话定位：是什么 + 给谁用 + 解决什么；确认是**生产系统**还是用户误把原型当目标（误则纠正） |
| 2. 终极目标 | 3–6 条，**编号列表**（prd 功能项 `goal_ref` 将引用编号，编号一经写入 goal.md 不复用）；每条须可落到真实能力，禁止「演示通路」 |
| 3. 核心价值 | 价值 → 说明 表格 |
| 4. 边界范围 | In Scope 摘要 + Out of Scope 表（非目标 + 原因）；**默认写入**排除项：MVP/demo 交付、主路径 stub/mock/假服务、假绿冒充已交付 |
| 5. 成功指标 | 走下方「可判定性环节」 |
| 6. 文档层级 | 固定生成下方结构图，无需提问 |

### Out of Scope 默认排除（可按项目改写措辞，不可删意图）

写入「4. 边界范围」时，至少覆盖：

- 不以演示/原型质量作为正式交付标准
- 非测试主路径不接受 stub、mock 假服务、假成功、骨架冒充已实现
- 不把「有入口但未接真实依赖」计为成功

### 成功指标可判定性环节

对用户给出的每条指标追问一次：「agent 如何判定这条达成 / 未达成？判定路径是否走真实依赖（非 mock）？」

| 类型 | 处理 |
|------|------|
| 可判定且真实路径（如「成功请求 100% 写入 usage」） | 写成可测试句式 |
| 仅演示可判定（如「点按钮有弹窗」） | **拒绝**作为正式指标；改写为业务正确性 / 可靠性 / 可运维指标 |
| 不可判定（如「≤1 工作日上线新厂商」） | 保留但标注 `（方向性）` |

## 重复执行（goal.md 已存在）

1. 读现有 goal.md，对照代码现状与 `git log`，列出疑似 **模糊 / 过时 / 与现状冲突 / MVP·demo 残留 / 鼓励假交付** 的条目
2. 按「质量评分」给出现状分数、扣分原因、建议动作
3. 逐条向用户提问确认（一次一条）
4. 汇总修订摘要（改了哪节、为什么）→ 用户确认后写入
5. **禁止**未经用户确认改写任何已有内容
6. 终极目标编号变更（删除/合并）时，提示受影响的 prd `goal_ref` 列表

## 产出结构

节标题固定，内容按探讨结果填写：

```markdown
# <项目名> — 产品目标

> 功能真理源见 prd.md；本文件低频人工修订（create-evolution-goal），演化 agent 只读。
> 定位：大型生产系统方向锚点。禁止将 MVP/demo/玩具验证写为正式目标。

## 1. 产品定义
## 2. 终极目标
## 3. 核心价值
## 4. 边界范围
## 5. 成功指标
## 6. 文档层级
```

「## 6. 文档层级」节固定写入：

```
docs/automate/goal.md              ← 方向与边界（人工低频修订，create-evolution-goal）
docs/automate/prd.md               ← PRD hub：8 维评分、依赖性评分、薄弱项、功能索引（G2 只读）
docs/automate/prd/                 ← 功能明细分片（按 ID 按需读）
docs/automate/plan.md              ← 里程碑（人工维护，create-evolution-plan；演化 agent 只读）
docs/automate/evolution-state.md   ← 当前轮次、待办池、模块地图、项目 skill/rule 索引、STUCK 计数
docs/automate/subagent/            ← subagent 外置提示词（可选，人工维护）
```

## 交互式引导问题库

按需使用，一次只问一个：

| 场景 | 问题 |
|------|------|
| 定位含糊 | “这句话里的用户、场景、要解决的生产问题分别是什么？” |
| 目标像 demo | “若去掉‘能演示’，这条目标用哪条可观测生产结果来定义达成？” |
| 范围过大 | “首版生产范围里，哪一块可以明确放进 Out of Scope，而不降低已纳入项的交付标准？” |
| 指标主观 | “agent 或自动化测试如何判定达成？判定是否允许走 mock？”（答案若为允许 mock → 改写指标） |
| 边界缺失 | “是否把主路径 stub/假服务/假绿明确写进 Out of Scope？” |
| 称呼过载 | “这句话里的『用户』是指终端操作者、租户管理员，还是接入方系统账号？” |
| 边界抽象 | “举个具体请求/事件：它算 In Scope 还是 Out？为什么？” |

## 红线

- 修订必须逐条经用户确认
- 写入前必须展示预览并获得确认
- **禁止**演化流程调用本 skill
- **禁止**把 MVP / demo / 玩具验证 / 「先 mock 再补真」写进正式 goal
- **禁止**成功指标以「可演示」「有界面」作为达成判据
- 产出后提醒用户：goal 修订可能影响 prd `goal_ref` 映射，建议接着跑 `create-evolution-prd` 体检
