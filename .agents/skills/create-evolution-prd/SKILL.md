# Create Evolution PRD（人工交互）

## 何时使用

- 用户手动触发（完整模式：新建 / 体检 / 迁移 / 修订）
- **场景 A（首次）**：`docs/automate/prd.md` 不存在
- **场景 B（存量体检）**：prd.md 已存在（单文件旧格式或 hub+分片）
- **禁止**被无人值守演化流程调用完整模式（无人值守的 prd 生成走 `doc-bootstrap` + `prd-bootstrap`）
- **例外 · `honest-writeback`**：仅 [loop-goal-prd](../loop-goal-prd/SKILL.md) / [go-fast](../go-fast/SKILL.md) 在合回且真实验收后，按下方子集回写分片**状态**（见「mode: honest-writeback」）

## 生产姿态（全程强制）

PRD 是大型生产系统的**功能真理源**：每一条「已实现」都必须是真实、可运维、可验收的能力，不是演示通路。

**前移细节（强制）**：首次生成 / 扩面修订的目标是**生产级可交付规格**，不是「够选题的骨架」。细节应写在 PRD 里，而不是留给后期演化轮次去「发明需求」。密度标准见 [references/production-density.md](references/production-density.md)。

| 禁止 | 要求 |
|------|------|
| 验收标准允许 mock/stub/假服务通过 | 验收必须走真实依赖与真实主路径 |
| 用「能演示」「页面能点」定义完成 | 完成 = 业务正确 + 真实集成 + 可观察结果 |
| 有入口但骨架/假数据/按钮无动作仍标「部分实现/已实现」 | 有入口则须真实可用，否则撤入口或标「未实现」并写清缺口 |
| MVP/demo 作为功能项交付定义 | 可用「首版范围更小的真实功能」，不可降验收标准 |
| 把测试双当成生产验收 | `*_test` / fixture mock **不得**计入功能验收通过 |
| 每项仅 2–4 条笼统验收就宣称首版 PRD 完成 | 普通项 **≥8** 勾选、底座 **≥10**；先能力矩阵再落 ID |
| 以「空仓 / 绿场」为由少写功能面或验收 | 绿场仍按生产表面铺 ID 与验收；锚点可标规划，验收不可降级 |
| 把「等 loop / 抛光再补需求」当作正常流程 | 后期演化只实现与抬状态；补能力面须走人工**修订** |

与 [code-reviewer](../code-reviewer/SKILL.md) 对齐：**非测试主路径 stub/假绿零容忍**；本 skill 在文档层禁止把它们写成可验收完成态。

## 文档定位

`docs/automate/prd.md` 与 `docs/automate/prd/*.md` 是自我演化的**功能真理源**，回答「系统有哪些功能、每个功能做到什么程度、如何验收、优先修哪里」。G2 只读 hub 选题；P1/P3/P5 按 prd ID 读取分片。

| 文档 | 定位 | 本 skill 是否修改 |
|------|------|------------------|
| `goal.md` | 产品方向与边界，提供 `goal_ref` 编号 | 否，缺失则引导先创建 |
| `prd.md` | PRD hub：薄弱项汇总、8 维总表、依赖性评分、功能索引、修订记录 | 是 |
| `prd/*.md` | 功能分片：状态、验收标准、代码锚点、goal_ref、依赖/被依赖 | 是 |
| `plan.md` | 人工里程碑排序 | 否，内嵌里程碑迁移交给 `create-evolution-plan` |
| `evolution-state.md` | 运行态与跨轮缓存 | 否 |

## 工作模式

| 模式 | 触发 | 输出 |
|------|------|------|
| 新建 | PRD 缺失 | hub + 分片 + `prd/README.md`（生产级密度） |
| 体检 | PRD 已存在 | 质量评分 + 漂移清单 + 修复方案（含稀疏验收） |
| 迁移 | 单文件旧格式 | 用户确认后的 hub+分片结构 |
| 修订 | 用户要求调整功能项/验收标准，或补密度/扩面 | 最小范围修改 + 修订记录 |
| **honest-writeback** | loop-goal-prd / go-fast 合回且真实验收后 | 仅更新指定分片**状态枚举**（及 hub 索引状态列若有）；见下节 |

## mode: honest-writeback（loop / go-fast 专用子集）

**允许**：

- 将已通过真实验收的分片状态改为 `已实现`（或诚实的 `部分实现`）
- 假绿/未通过 → 降为 `未实现` / `部分实现`，或保持原状并拒绝抬升
- 同步 hub 功能索引中对应状态列（若存在）

**禁止**：

- 改写验收标准、新增功能域/分片、改 `goal_ref`、大改依赖图
- 未经真实验收标「已实现」
- 跑完整「新建/体检/迁移/修订」交互或无人值守发明需求
- 改 `goal.md` / `plan.md`（plan 勾选走 create-evolution-plan 的同名子集）

**写者**：默认由 go-fast 执行（见 [loop-orchestrator-contract.md](../go-fast/references/loop-orchestrator-contract.md) §3）；编排方仅校验，漏写可按本子集补写。  
**无需**用户预览确认（调用方已通过合回+相关测门）；仍须在调用方 `summary` 列出 ID。

> 实现后若需把测试名/真实锚点写进勾选框：走人工 **修订**（只追加证据，不删生产语义），**不要**塞进 honest-writeback。

## 提问纪律

- 一次一个问题，可选项优先；用户跳过 → 推荐默认值 + `（待确认）` 标注
- 写入前必须展示「影响范围 + 变更摘要 + 将写入/迁移的文件列表」，等待用户明确确认
- **写入预览必须含密度指标**：功能项总数、验收勾选总数、每项平均勾选数（目标均值 **≥8**）；不达标不得请求确认写入
- 用户提出「先 mock 验收 / 先做 demo 功能」→ **拒绝写入该验收句**，改写为真实路径或缩小功能范围
- 用户提出「先写骨架、以后再补细」→ **拒绝**：说明前移细节是本 skill 默认；可缩小 **In Scope 功能项集合**，不可降低已纳入项的验收密度
- **功能名与 goal 口径一致**：分片名用已钉死的业务称呼；过载词当场消歧，禁止同一概念多别名散落各分片
- **验收起草用具体场景**：禁止只写「体验更好」；须满足下方「分片验收与状态纪律」密度门
- **声称已实现须对账代码**：用户或旧 PRD 标「已实现」时，对照锚点是否真通；矛盾 → 降状态或重写验收，勿采信口述

## 质量评分（100 分）

| 维度 | 分值 | 检查点 |
|------|-----:|--------|
| 覆盖完整度 | 10 | 核心域与关键用户路径有功能项；**能力矩阵**对账 goal/arch/baseline/prototype；核心域项数达密度表下限 |
| 功能粒度 | 10 | 功能项可独立**真实验收**；禁止过大「大包」或过碎无法交付；一项一生产能力 |
| goal_ref 对齐 | 10 | 每项映射到稳定终极目标编号 |
| 验收标准可判定性 | 15 | 可测试、可观察；**普通项 ≥8 / 底座 ≥10 勾选**；强制维 A–F 覆盖；显式排除 mock/stub |
| 生产诚实性 | 15 | 无 MVP/demo 完成定义；状态与入口/真实依赖一致；无假绿友好验收；无「空仓少写」借口 |
| 8 维评分有效性 | 10 | 评分有证据、刻度统一、避免整行同分 |
| 代码锚点准确性 | 10 | 锚点路径存在或明确「规划：」；能支持后续 P1/P3；锚点若为 stub 不得支撑「已实现」 |
| 依赖性评分有效性 | 10 | hub 有 `依赖性` 列，分片有 `被依赖` 与 `依赖性评分` |
| 状态一致性 | 5 | hub、分片、plan 勾选无矛盾 |
| 可维护性 | 5 | 修订记录 ≤10 条，hub 不堆历史噪音 |

评分解释：

| 分数 | 结论 |
|------|------|
| 90-100 | 可稳定驱动 G2 选题与 P5 重评 |
| 80-89 | 可用，但需要补齐少量映射或验收标准 |
| 70-79 | 能启动，但选题和合并后重评会偏脆 |
| <70 | 建议先继续体检/迁移，不进入无人值守演化 |

**硬门槛**：

- 任一分片用 mock/stub 定义验收通过，或「已实现」对应假绿入口 → 「生产诚实性」0 分，总分上限 **69**
- 任意功能项验收勾选 **&lt;6**，或核心域未做能力矩阵对账 → 「验收标准可判定性」封顶 **8/15**，场景 A / 扩面修订 **不得**标 `DONE`（须 `DONE_WITH_CONCERNS` 或继续补）

## 分片验收与状态纪律

### 验收标准写法（生产级密度 · 强制）

完整规则：[references/production-density.md](references/production-density.md)。

**数量**：普通项 **≥8** 勾选；依赖性 ≥80 的底座项 **≥10**；推荐 8–12（底座 12–16）。历史「至少 2 条」仅为绝对底线，**不作为首版完成标准**。

每条勾选建议含：

1. **触发**：谁在什么界面/API 触发
2. **真实路径**：经过哪些真实服务/存储/外部依赖（点名，禁止「或 mock」）
3. **可观察结果**：数据落库、审计、响应字段、副作用
4. **失败诚实性**：依赖失败时不得返回假成功

**强制覆盖维**（每项须覆盖 A–F，缺维写 N/A 理由；有 UI 加 G；arch 已定分布式语义加 H）：

| 维 | 含义 |
|----|------|
| A 主路径 | 真实成功结果 |
| B 权限/隔离 | 越权拒绝 |
| C 失败诚实 | 依赖不可用 |
| D 状态机/边界 | 过期/重复/并发/幂等 |
| E 可运维信号 | 审计/指标/日志之一 |
| F 配置/生效 | 配置变更与错误配置 |
| G UI 闭环 | 空态/加载/字段错误（有前端时） |
| H 分布式 | 跨节点/扇出/Job 等（arch 已定时） |

模板句式：

```text
给定 <前置真实数据/权限>，当 <真实操作>，则 <可观察结果>；
依赖 <X> 不可用时，返回 <明确错误/降级策略>，不得返回成功态。
```

### 状态枚举含义（强制）

| 状态 | 含义 |
|------|------|
| 未实现 | 无可用主路径，或仅有规划 |
| 部分实现 | **真实主路径已打通一部分**；缺口清单明确；**禁止**用 stub 冒充已通部分 |
| 已实现 | 验收标准全部可在真实依赖下通过；入口完整；无假数据冒充 |
| 已废弃 | 不再交付；入口与宣称已撤 |

发现「有菜单/路由但骨架屏/假数据/按钮无动作」→ 状态不得高于「未实现」（或「部分实现」且验收写明缺口与禁止宣称可用）。

## 场景 A：首次生成

1. 前置：goal.md 须存在；缺失 → 引导先跑 `create-evolution-goal`
2. 收集输入面（有则读，无则记录缺口，**不**因此降验收密度）：
   - `docs/arch.md`（已定决策必须进验收）
   - `docs/tt.md` / 基线 / 对标原型（用户点名的路径或产品名）
   - 代码路由/API/包（有界扫描；绿场可空）
3. 提议**域划分**（按目录结构 / 路由面 / goal In Scope 反推）→ 用户确认或调整
4. **能力矩阵**（见 density 文档）：按域列出用户可感知能力行 → 展示每域行数与拟增 ID → 用户确认或裁剪 **In Scope 集合**（裁剪的是做不做，不是验收写多粗）
5. 逐域确认功能项与粒度（一次一域）；粒度以「可独立真实验收的生产能力」为准；**核心域项数须达 density 下限**；过大则拆，过碎则合并但合并后勾选不减
6. 按 `prd-bootstrap` 的有界扫描流程补代码锚点（目录预算同其规定）；扫到 stub → 锚点可记，但状态/验收不得写成已完成；无代码 → 锚点前缀 `规划：`
7. **goal_ref 映射**：按域批量向用户确认每项对应 goal.md 终极目标编号
8. 为每项起草**生产级密度**验收（强制维 A–F + 适用的 G/H），逐域确认；预览报平均勾选数
9. 加载 `prd-scoring` 做 8 维子项初评（0/1/2 + N/A，算维度分%与加权总分；附证据，禁止整行同分）
10. 建立功能依赖图：从每项 `依赖`、验收标准、代码锚点、公共模块/路由/配置关系抽取入边 → 填 `被依赖` 与 `依赖性评分`（0=无被依赖，100=核心底座）
11. 写 hub + 分片 + `prd/README.md`
12. 回传 `summary` 必须含：功能项数、勾选总数、平均勾选、矩阵对账结论（arch 决策是否均有落点）

## 场景 B：存量体检

### B1. 结构检查

| 现状 | 动作 |
|------|------|
| 单文件旧格式（无 `evolution_hub: true`） | 提议迁移：按域拆条目 → 用户确认域划分 → 生成分片 + 按 hub 模板重写 prd.md |
| 已是 hub+分片 | 进入 B2 |

### B2. 漂移体检清单（逐项检查并报告）

| # | 检查项 | 修复动作 |
|---|--------|----------|
| 1 | 薄弱项汇总区堆积历史 note / blockquote | 列出行数 → 整段删除（历史进修订记录或丢弃） |
| 2 | 状态双写矛盾（hub Backlog 表 vs 里程碑表 vs 分片） | 列出冲突条目 → **逐条问用户以哪处为准** → 单点化到分片，删除 hub 冗余状态表 |
| 3 | 修订记录 >10 条 | 裁剪到最近 10 条 |
| 4 | 状态枚举不统一（英文 / 混用） | 替换为 `未实现 · 部分实现 · 已实现 · 已废弃` |
| 5 | 功能项缺 `goal_ref` | 按域批量向用户确认映射 |
| 6 | 里程碑内嵌 prd.md | **本 skill 不动里程碑**；提示用 `create-evolution-plan` 迁移 |
| 7 | hub 总表为旧评分刻度（`/40`、各维 `1–5`、总分列） | 提议升级到 `prd-scoring` 新模型（维度分% + 加权总分 0–100）：仅换表头与刻度结构，**不重评分值**；旧分值标 `待重评`，留待 P5 触及时按子项重评 |
| 8 | 功能项验收标准不可判定（如“体验更好”“足够稳定”） | 列出条目 → 逐项追问用户如何判定达成 |
| 9 | 代码锚点缺失或明显过期 | 有界扫描相关目录，提出候选锚点 → 用户确认后写入 |
| 10 | hub 功能索引缺分片或分片无索引 | 补齐索引；完全无法定位的功能项先询问用户归属域 |
| 11 | 历史 PRD 缺 `依赖性` 列，或分片缺 `被依赖` / `依赖性评分` | 提议升级依赖性评分结构 |
| 12 | **假绿/ stub 验收**（验收句含 mock/stub/demo，或「已实现」对应假入口） | 降状态 + 重写验收为真实路径；必要时建议跑 code-reviewer |
| 13 | **MVP/demo 措辞**出现在功能定义或完成标准 | 改写为生产范围与真实验收；不保留 demo 完成定义 |
| 14 | 有入口半成品（骨架/假数据/残交互）仍标部分实现/已实现 | 与用户确认：撤入口、降状态、或补真实实现后再验收 |
| 15 | **同一概念多名**（分片/验收/goal 称呼冲突） | 统一为 goal 或已确认规范名；旧别名写入「避免混用」备注或删 |
| 16 | **验收密度不足**（任一项勾选 &lt;6，或域平均 &lt;8，或仅成功+失败两条） | 提议修订扩勾选（强制维 A–F）；影响范围列 ID 列表；用户确认后执行 |
| 17 | **能力面缺口**（arch/原型/goal In Scope 有能力无 PRD ID） | 提议修订新增 ID 或并入既有项验收；展示矩阵差集 |
| 18 | 分片头仍写「空仓初评」但代码/状态已演进 | 更新分片头说明；锚点从「规划」升为真实路径（若存在） |

### B2.1 依赖性评分升级

当旧 PRD 没有依赖性评分时：

1. 先报告“旧格式兼容：缺失依赖性评分不会导致 PRD 无效”
2. 向用户提议升级，说明影响范围：
   - `docs/automate/prd.md`：8 维总表新增 `依赖性` 列，薄弱项汇总新增 `依赖性`
   - `docs/automate/prd/*.md`：每个功能项新增 `被依赖` 与 `依赖性评分`
3. 建立依赖图：
   - 显式边：分片里的 `依赖` 字段、验收标准中引用的 prd ID
   - 结构边：共享核心模块、公共 API、公共 UI 组件、认证/权限/配置/任务调度/存储等基础链路
   - 代码边：有界扫描代码锚点，最多深入 3 个相关一级模块；不做全仓扫描
4. 评分规则引用 `prd-scoring` 的「依赖性评分」：
   - 0 = 没有被依赖
   - 分数越高 = 被其他功能/模块依赖越多、越跨域、越阻塞后续开发
5. 对不确定边标 `（待确认）`，禁止臆造；必要时逐条问用户确认
6. 写入前展示升级预览和分值摘要，用户确认后执行

### B3. 执行

1. 输出体检评分（100 分）与扣分原因（含密度：平均勾选、&lt;6 项清单）
2. 输出修复清单（每项：问题 → 动作 → 影响范围 → 是否需要用户裁决）
3. 展示写入预览：新增/修改/删除文件列表，迁移前后结构摘要，**密度前后对比**
4. 用户确认后批量执行
5. 执行后在 hub 修订记录追加一条「人工体检（create-evolution-prd）」

## 交互式引导问题库

按需使用，一次只问一个：

| 场景 | 问题 |
|------|------|
| 域划分不清 | “这些功能更像同一业务域，还是应该拆成 &lt;A&gt;/&lt;B&gt; 两个域？” |
| 功能粒度过大 | “这个功能能否拆成可独立真实验收的 2-3 个生产能力项？” |
| 能力面裁剪 | “矩阵里这些行要纳入首版 In Scope，还是标 Out of Scope？（裁剪范围，不降低已纳入项的验收密度）” |
| 验收过稀 | “该项目前不足 8 条勾选；补权限/失败/幂等/审计/配置生效哪几条？还是拆成多项？” |
| goal_ref 缺失 | “这个功能主要服务 goal.md 里的哪一个终极目标编号？” |
| 验收标准模糊 | “agent 怎么判断达成？判定路径是否允许 mock？”（允许 → 改写） |
| 缺失败场景 | “依赖 X 超时或鉴权失败时，验收句期望看到什么？（禁止仍返回成功）” |
| 称呼冲突 | “分片里的『账号』与 goal 里的『用户』是否同一概念？采用哪一个规范名？” |
| 假绿嫌疑 | “当前入口后面是真实服务还是 stub/假数据？若是后者，状态应降为未实现还是撤入口？” |
| 外部集成无契约 | “该对接的官方 SDK/协议文档或沙箱是否已具备？若否，先跑 integration-research，状态保持未实现。” |
| 状态矛盾 | “hub 与分片状态冲突，以哪一个为准？” |
| 依赖性不确定 | “这个功能是被哪些功能依赖，还是主要依赖别人、自己不被依赖？” |
| 高依赖评分 | “这个功能未完成时会阻塞哪些后续模块开发？” |
| 对标原型 | “对标产品的哪些能力面必须进首版 PRD？（列出后进入矩阵，禁止只写口号级一项）” |

## 红线

- 体检只修结构与漂移，**不重评全部 8 维**（重评属 P5 / 初评属场景 A）
- 状态矛盾必须经用户裁决，禁止自行猜测（**例外**：`honest-writeback` 仅按真实验收结果升降状态，不裁决产品方向）
- 写入前必须展示预览并获得确认（**例外**：`honest-writeback`）
- 不改 `goal.md`、不改 `plan.md`
- **禁止**演化 Automation / 演化 subagent 调用完整模式；**允许** loop-goal-prd / go-fast 仅以 `honest-writeback` 回写状态
- **禁止**`honest-writeback` 改验收句、新功能域或发明分片
- **禁止**验收标准以 stub/mock/假服务/demo 作为通过条件
- **禁止**将有入口的半成品标为「已实现」
- **禁止**把 MVP/demo 完成定义写入正式分片
- **禁止**以稀疏验收（普通项 &lt;8 / 底座 &lt;10）完成场景 A 并标 `DONE`
- **禁止**跳过能力矩阵、仅按 goal 口号生成「域级骨架 PRD」
