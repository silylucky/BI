# PRD 生产级密度（首次生成强制）

> 目标：首次 `/create-evolution-prd` 就把可验收细节写够，减少后期靠演化轮次「补需求」的成本。  
> 本文件被 [SKILL.md](../SKILL.md) 引用；写分片前必读。

## 1. 为什么要前移细节

| 稀疏初评（旧默认） | 生产级初评（新默认） |
|--------------------|----------------------|
| 每项 2–4 条笼统验收 | 每项 **8–12** 条可判定场景（底座可到 12–16） |
| 只写 goal 口号级能力 | 先铺 **能力矩阵** 再落 ID |
| 后期靠 loop 补 ID/验收 | 后期只做实现 + honest-writeback 抬状态 |
| 「能开工」即 DONE | 「能按验收独立交付生产能力」才 DONE |

实现后可追加「证据勾选」（测试名/锚点），但**不得**把「等演化再补需求面」当作正常流程。

## 2. 能力矩阵（写入分片前）

对每个业务域填矩阵，行=用户可感知能力，列=来源：

| 列 | 来源 |
|----|------|
| goal | `goal.md` In Scope / 成功指标 |
| arch | `docs/arch.md` 已定决策（Fanout/Job/国密/存储…） |
| baseline | `docs/tt.md` / 招标基线 / 白皮书（若有） |
| prototype | 对标产品能力面（用户点名的原型仓或公开能力清单） |
| code | 路由 / API / 包目录（有界扫描；绿场可空） |
| ops | 交付/HA/观测/审计/权限联验 |

规则：

1. 矩阵行若无对应 PRD ID → **必须新建功能项**或并入已有项的验收勾选（并注明归属）
2. arch 已钉死、PRD 无验收 → **硬缺口**，禁止宣称 PRD 可驱动生产交付
3. Out of Scope / 未钉厂商 → 写「方向性 + 禁止宣称完成」，**不**写假验收通过
4. 用户确认域划分后，**展示矩阵摘要**（每域行数 + 拟增 ID 数），再写分片

### 域内功能项数量下限（首版）

| 域类型 | 建议功能项数 | 说明 |
|--------|:------------:|------|
| 核心业务域（IM/交易/监控主路径等） | **6–14** | 禁止用 2–3 个「大包」糊弄 |
| 平台底座（AUTH/权限/会话） | **4–8** | 登录/会话/身份模型/RBAC/企业 IdP 宜拆开 |
| 管理台 / 工作台壳 | **4–8** | 导航、权限表面、配置、策略分项 |
| 扩展生态（插件/集成） | **5–10** | 生命周期、宿主隔离、SDK、Webhook/Bot 等 |
| 交付 / 合规 / 观测 | **4–9** | 与 arch 决策一一对应验收 |

绿场无代码时仍按上表铺面；**禁止**以「空仓所以少写」降密度。

## 3. 单功能项验收勾选密度

### 数量

| 功能依赖等级 | 最少勾选 | 推荐 |
|--------------|:--------:|:----:|
| 依赖性评分 ≥80（底座） | **10** | 12–16 |
| 普通业务项 | **8** | 8–12 |
| 纯文档/方向性交付项 | **6** | 6–8 |

**硬门槛**：任意功能项勾选 **&lt;6** → 质量分「验收标准可判定性」封顶 8/15，且场景 A **不得**标 DONE（须补齐或拆项）。

### 强制覆盖维（每项至少命中下列 6 维；缺维须标注 N/A 理由）

| 维 | 必须回答的问题 |
|----|----------------|
| A 主路径 | 授权角色在真实 UI **或** API 触发后，真实存储/外部依赖上的可观察成功结果 |
| B 权限/隔离 | 无权限、跨租户/跨团队、越权深链 → 明确拒绝，不得假空成功 |
| C 失败诚实 | 存储/缓存/外部依赖不可用 → 明确错误，不得假成功 |
| D 状态机/边界 | 过期、重复提交、并发、部分成功、幂等键 |
| E 可运维信号 | 审计/指标/日志/request id 至少一类可观测（若域适用） |
| F 配置/生效 | 配置变更后何时生效；错误配置不得标「已接通」 |

有前端表面的项另加：

| 维 | 要求 |
|----|------|
| G UI 闭环 | 加载中/空态/字段级错误/提交禁用或可重试；禁止「按钮无动作」可验收 |

有多实例/HA 的项另加（arch 已定则强制）：

| 维 | 要求 |
|----|------|
| H 分布式语义 | 跨节点一致、扇出、会话亲和、Job 无 worker 告警等 arch 已定语义 |

### 禁止的稀疏写法

- 只有「能登录 / 能发消息 / 体验更好」级句子
- 两条「成功 + 失败」就交差
- 把 5 个用户可感知能力揉进 1 个 ID，验收却只有 4 条
- 绿场写「等实现后再补验收」
- 用 mock/stub/demo 作为通过条件

### 句式（每条勾选尽量完整）

```text
给定 <真实前置数据/权限/配置>，当 <角色在界面或 API 执行操作>，
则 <落库/响应字段/副作用/审计或指标> 可观察；
当 <权限不足 | 依赖 X 失败 | 边界条件>，则 <明确错误或降级>，不得返回成功态。
```

一条勾选可只强调成功或只强调失败，但整项必须覆盖上表强制维。

## 4. 与后期演化的分工

| 阶段 | PRD 允许做什么 |
|------|----------------|
| 首次生成 / 修订扩面 | **扩 ID、写密验收、能力矩阵对账** |
| go-fast / loop honest-writeback | **只改状态**；禁止发明需求 |
| 实现后修订（人工） | 可**追加**证据勾选（测试名、真实锚点）；不删生产语义验收 |
| loop-polishing | 实现与抛光；缺口应来自已有验收，而非补写能力面 |

## 5. 自检清单（写入前）

- [ ] 每域有能力矩阵摘要，且 arch 已定决策均有 PRD 验收落点
- [ ] 核心域功能项数不低于上表下限
- [ ] 每项勾选 ≥6（底座 ≥10），强制维 A–F 已覆盖或声明 N/A
- [ ] 无 MVP/demo/mock 通过条件
- [ ] 绿场锚点可标「规划：」，但验收已是生产路径语义
- [ ] 预览中给出：功能项总数、勾选总数、每项平均勾选数（目标均值 ≥8）
