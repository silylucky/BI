# 流程图 / 架构图 / 真机截图

标杆模块若默认有图，待补模块必须同级对待，否则目录再全也像半成品说明书。

## 何时必须出图

| 文档类型 | 最低图要求 |
|----------|------------|
| 技术方案 | 每模块：业务流程图 + 模块组成/分层架构图；功能实现宜有 1–2 张真机界面 |
| 详细设计 | 同技术方案（放在对应小节后） |
| 集成实施 / 需求 | 目录含「系统界面示例 / 页面设计」则必须截图或图题；流程可用文字，有图更佳 |
| 初步设计 | 方案级可各 1 张总流程/组成图 |
| 数据库设计 | 一般不插业务流程图 |

以**同文档标杆**为准：标杆无图则不强行堆图；标杆有图则待补必须有。

## 风格

- **配色**：深蓝标题条 + 浅蓝流程框 + 白底；决策用浅黄菱形（可按用户原件微调）。  
- **泳道图**：横向阶段 / 纵向角色；步骤少而清（5–8 步）；主路径箭头清晰。  
- **模块组成图**：分层（应用 → 服务 → 数据 → 外部协同）或「中心模块 → 能力分组」。  
- **文字**：只用中文业务词；框内禁止 API 路径、表名、错误码、包名、函数名。  
- **可读**：一屏能看懂；宁可少步骤，勿密密麻麻状态机全集。

## 生成方式

工作区若已有生成脚本则复用。否则：

1. Python + Pillow（或等价）渲染 PNG；中文字体用系统黑体/苹方等。  
2. 命名建议：`flow-{module}.png`、`mod-{module}.png`。  
3. Markdown：

```markdown
![某模块业务流程](screenshots/diagrams/flow-xxx.png)

![某模块组成](screenshots/diagrams/mod-xxx.png)
```

4. 合并进 Word：脚本须识别 `![alt](path)` 或图题表并插入图片；合并后「插图未找到」为零。  
5. **勿用 Mermaid 源码充当终验插图**（除非用户只要 MD 预览）；交付 Word 需要栅格图。

### 内容从哪来

从扫描主流程**翻译**成角色步骤，例如：

```text
提交申请 → 审批 → 是否通过 → 开通资源 → 回写结果 → 审计留痕
```

不要把枚举值、表名、函数名画进框里。

## 真机截图

### 前置

用户提供或工作区 `.dev` / 本地 URL、账号（**勿把口令写进交付正文**）。

### 流程

1. 登录目标环境，按文档图题打开真实菜单页。  
2. 窗口最大化或固定宽度；去掉个人敏感信息；空态可截但图题勿夸大成「已配置完成」。  
3. 落盘：`screenshots/{system}/fig-{章号}-{序号}-slug.png`（路径随工作区约定）。  
4. 维护 `MANIFEST.md`：图号、图题、文件、状态（已截/部分/未截）。  
5. 正文：`以下为…界面示意：` + `![图题](相对路径)`。

### 禁止

- AI 生成假 UI 冒充系统截图。  
- 图题与画面不符且不在 MANIFEST 标明「部分」。  
- 同一张图复制多份改图题凑数。  
- 在截图说明里写暴露验收风险的环境吐槽——图可空态，正文写「支持…」能力即可。

## 自检

打开标杆章：流程后有无大图、模块后有无组成图、功能下有无界面。  
待补章是否**同构**？缺则补图，而不是再堆两页接口说明。
