# 文档类型深度档案

标题名以**用户模板目录原文**为准。下表是常见政企套件的合格深度与失败态；无标杆时作默认骨架。

---

## 需求规格

**合格**：字段级、状态、角色、提示；「系统功能」下拆进目录的功能点。  
**失败**：只有「系统功能描述」叶节点；或纯提纲。

```markdown
{模块名}
{总述}

### 业务流程
{角色与状态流转；可附流程图}

### 系统功能
#### 功能点甲
支持…。{角色}可…。
新增：…。编辑：…。筛选：…。

#### 功能点乙
…
```

---

## 技术方案

**合格**：业务可读的流程 / 模块 / 实现 + 图。  
**失败**：代码注释体、接口/错误码墙、函数名清单。

```markdown
{模块名}
{总起 2–4 句，业务定位，勿堆技术栈广告}

{x.1 业务流程}
**环节名A**
{角色做什么，如何流转}
**环节名B**
{…}
![模块业务流程](screenshots/diagrams/flow-xxx.png)

{x.2 系统模块}
**能力块1**
{职责说明}
![模块组成](screenshots/diagrams/mod-xxx.png)

{x.3 功能实现}
**功能名**
{短述可演示能力}
{可选：界面示意 + 截图}
```

---

## 详细设计

**合格**：技术方案下业务流程 / 系统模块 / 功能实现 + 图；可写组件与机制。  
**失败**：与技术方案同样的代码墙；或用薄稿冲掉原文已有细目。

```markdown
{模块名}
{技术方案}
{业务流程}  + 流程图
{系统模块}  + 组成/分层图
{功能实现}  {中文书面语，不作 API 清单墙}
```

合并时若原文细目已写满：**保留目录骨架**，收敛表述并补总图，勿覆盖可验收细目。

---

## 初步设计

**合格**：目标范围、功能块、关系；深度介于需求与详细设计之间。  
**失败**：抄需求全文或抄详细设计接口。

```markdown
{模块名}
{方案目标与范围}
{主要功能块（1）（2）（3）}
{关键流程概述；可附 1 张总图}
{与周边系统关系概述}
```

---

## 系统集成与实施

**合格**：流程 + 构成 + 界面 + 对接表；密度对齐同文档已完成运维/业务章。  
**失败**：四段标题下各三句话。

```markdown
{模块名}
{总起}

{业务流程}
总体流程为：
步骤A；
步骤B；
…
全过程{受控/可回溯}。

{系统功能}
由以下子系统构成：
子系统1（要点）；
子系统2（…）；

{系统界面示例}   # 目录有则写；真机截图或图题
以下为…界面示意…
![…](…)

{数据源与接口规范}
| 对接对象 | 主要内容 | 对接方式 | 实时性 |
```

对接表列名以模板为准；实时性常用「实时」「准实时」。

---

## 数据库设计

**合格**：真实表、字段级；列名与同章已有表一致。  
**失败**：把 API 说明写进数据库章；写 Repository 方法。

只写扫描到的真实持久化对象；无表则不硬编。

---

## 跨文档同模块

| 文档 | 强调 |
|------|------|
| 需求 | 谁可做什么、字段与提示 |
| 技术方案 | 为什么这样划分、主链路与图 |
| 详细设计 | 组件职责与机制（仍禁路径墙） |
| 集成实施 | 如何落地、对接与界面 |
| 数据库 | 存什么 |

能力同源；禁止三份文档事实互相矛盾。
