# 文风与禁写项（政企验收）

## 读者

政企验收方与业务领导，**不是**仓库维护者。能朗读给非开发听懂才合格。

## 语气与称谓

- 正式、书面、可预读、可验收：写清「谁、在什么状态、做什么、如何流转、如何留痕」。  
- **禁止**：「我方」「甲方」「你方」「贵方」「我们」「你们」「咱们」。  
- 主语优先：「系统 / 平台 / 本模块 / 管理人员 / 运维人员 / 支持…」。  
- 角色用岗位或业务角色（管理员、审批人、值班人员），不用「用户方」「建设方」对抗表述。  
- 专名与目录一致；英文专名保持常见写法（API、CMDB、RTO、RPO、SSO）；首次可中英并列。

## 段落节奏（技术方案 / 详细设计常见）

1. **模块总起**：1 段定位（职责 + 在平台中的位置），约 2–4 句。  
2. **业务流程**：若干加粗小标题 + 短段角色叙事；段落后接流程图（若标杆有）。  
3. **系统模块**：按能力块加粗小标题 + 短段；段落后接组成/架构图。  
4. **功能实现**：再按功能块短述；必要时界面示意 + 真机截图。  

不要用「一、二、三、」技术白皮书腔替代标杆骨架（除非该文档标杆本身如此）。

## 代码证据 → 正文

| 扫描到的 | 正文应写成 | 禁止直接粘贴 |
|----------|------------|--------------|
| 状态枚举 | 过程可追溯的业务状态叙述 | 码表墙 |
| HTTP/RPC 路径 | 「提供××能力 / 与××系统交互」 | 路径墙 |
| 类/函数/方法名 | （通常不出现） | 标识符刷屏 |
| 包路径 / 文件路径 | （不进正文） | `server/internal/...` |
| 错误码常量 | 「未满足条件时不得…」 | 错误码附录 |
| 表名（非数据库文档） | 「受控变更进入待审…」 | DDL/字段清单进方案正文 |
| mock / 联调开关 | （不写） | 生产能力含 mock |

**技术方案 / 详细设计**：组件职责语言（控制面、执行器、适配层、审计），不要配置缺省值大表。  
**需求 / 集成实施**：可写到字段、按钮、状态、提示原文。  
**数据库设计**：才写表名字段级（仍避免 ORM/Repository 方法名）。

## 性能与容量

仅写代码/配置/既有需求中出现的数字。  
RTO/RPO：写成探测 / 切换日志等证据口径；禁止无依据硬 SLA，也禁止「未保证」自我暴露。

## 界面与图

- 「以下为…界面示意」+ 真机 PNG；见 [diagram-screenshot.md](diagram-screenshot.md)。  
- 不生成假 UI；不伪称已插入二进制。  
- 图题用业务名。

## Word / 目录

- 标题样式须能进智能目录；outline 层级与模板一致。  
- **禁止双重编号**：手写 `2.1.5` + 样式再自动编号。  
- 合并后提醒更新整个目录；抽检插图与标题树。

## 终验红线（禁止）

- 互联网营销腔、无关行业案例。  
- 泄露账号口令到对外稿。  
- 同一概念多名混用且不定义。  
- **标杆外尾巴章**（补充机制、错误码附录、修订说明、加厚版说明…）。  
- **重复段落改序号凑篇幅**。  
- **自我暴露缺口**（未对接 / 不含 / 前端未开放 / 验收不以××为准）。  
- **点名未交付对端**（即便否定句）。  
- **全篇代码风格无法预读**（路径、反引号标识符、错误码表、DSN、函数/方法名清单）。  
- **把扫描用 mock/联调开关写进生产能力清单**。  
- **合同对抗称谓**（我方/甲方/你方等）。
