# Grilling（穷追追问）

就此事的**每一个方面**持续访谈，直到我们达成共同理解。沿决策树逐分支走下去，**一次解开一个**决策依赖。每个问题都给出你的**推荐答案**。

**一次只问一个问题**，等反馈后再继续。一次抛多个问题会让人懵。

若某个*事实*可通过探索环境（文件系统、工具等）得到，**自己查**，不要问我。*决策*才是我的——每个决策都抛给我，并等待回答。

在我确认我们已达成共同理解之前，**不要**据此动手实现或改文档真理源。

## 模式

| mode | 行为 |
|------|------|
| `plain`（默认） | 只追问，不落盘 |
| `with-docs` | 追问节奏不变；在达成共识的瞬间把结果**写进文档**（术语对齐 + 稀疏 ADR），不要攒到最后 |

### mode=with-docs 额外做什么

**术语（当场钉死）**：用户或对话出现过载/冲突称呼时：提出规范名 +「避免混用」，写入合适位置（优先已有 `docs/domain/`、arch/goal 口径；没有则懒创建简短术语表，**只写叫什么，不写实现细节**）。

**ADR（稀疏）**：仅当三者同时成立时，才提议写 `docs/adr/<主题>-<模块|流程>.md`（或仓内既有 ADR 约定）：

1. **难回退** — 事后改主意成本高  
2. **无上下文会惊讶** — 后人会问「为什么这样」  
3. **真有取舍** — 有过真实备选并因具体理由选了其一  

缺一则不写 ADR；一句话记在对话或 arch 决策节即可。

**with-docs 纪律**：追问节奏与 plain 相同（一次一问；事实自查，决策问用户）；未确认共同理解前，不擅自大改业务代码；写入前展示将落盘的术语/ADR 预览，用户点头再写。

## 边界

若要对**已有业务系统/流程/模块/页面**直接下结论并出改造方案（而非一次一问），改用 [product-reviewer](../product-reviewer/SKILL.md)。  
若要**少问 + 完整业务蓝图/业内场景对照/一稿确认**（或对照 PRD 偏航、出开工规格），改用 [product-blueprint](../product-blueprint/SKILL.md)（内嵌有限 grilling 硬决策，默认 ≤3 问；强制架构图+核心业务流程各一图、确认面先图后文）。
