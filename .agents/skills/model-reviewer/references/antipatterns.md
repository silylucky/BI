# 数据模型反模式目录（含检测线索）

扫描时逐条对照。`检测线索` 是**起点**不是判据——命中后必须读真源确认，再写 finding。
默认级别可按业务影响上调或下调，但**下调必须写理由**。

检索式按 [code-scanning](../../code-scanning/SKILL.md) 三层分诊：rg 找关键词 → ast-grep 找 ORM 结构 →
codegraph 找消费方。示例用 rg，路径按 Model Card 的真源替换（`migrations/`、`db/ddl/`、`prisma/`、`models/`）。

---

## A. 身份与唯一性

| # | 反模式 | 为什么坏 | 默认级 | 检测线索 |
|--:|--------|----------|:--:|----------|
| A1 | **业务自然键无唯一约束** | 并发下「先查后插」必漏；重复用户/重复订单入库后极难清理 | **P0** | 表有 `code`/`no`/`sn`/`email`/`phone`/`order_no` 列但 DDL 无对应 `UNIQUE`：`rg -n 'CREATE TABLE|UNIQUE' <真源>` 后逐表比对 |
| A2 | 可变业务字段做主键 | 改一次手机号要级联全库 | P0 | `PRIMARY KEY *(*(email|phone|code|name)` |
| A3 | 随机 UUIDv4 作聚簇主键（大表） | InnoDB 页分裂、写放大、索引膨胀 | P1 | `char(36)`/`uuid` 主键 + 该表为高写入主表 |
| A4 | 无幂等键的对外写接口表 | 网络重试造成重复业务单据 | P1 | 支付/下单/回调表无 `*_no`/`idempotency*` 唯一键 |
| A5 | 跨表引用类型不一致 | 隐式转换 → 索引失效 | P1 | 同名 id 列在不同表类型/长度不同 |

## B. 关系与结构

| # | 反模式 | 为什么坏 | 默认级 | 检测线索 |
|--:|--------|----------|:--:|----------|
| B1 | **逗号分隔列表**（jaywalking） | 不能约束/索引/join；改一次扫全表字符串 | P0 | 列名 `*_ids`/`*_list`/`tags` 且类型为 varchar/text |
| B2 | **上帝表** | 混多概念多生命周期，改动牵连、锁竞争 | P1 | 单表列数异常多（>40 参考值）或列名前缀分明成多组 |
| B3 | 重复列组 `addr1/addr2/addr3` | 数量一变就要 DDL；无法排序统计 | P1 | `rg -n '\b\w+_?[123]\b'` 命中同前缀连号列 |
| B4 | 业务已知属性用 **EAV** | 类型/约束/查询/报表全退化 | P1 | 表含 `attr_name`+`attr_value` 或 `key`+`value` 且被业务主流程消费 |
| B5 | 多态外键无校验无对账 | 引用可悬空，无法保证完整性 | P1 | `*_type` + `*_id` 成对出现且无 FK、无清理任务 |
| B6 | M:N 缺关联表（靠 JSON/列表硬凑） | 见 B1，且无法带关联属性 | P1 | 同 B1，且业务上明显是多对多 |
| B7 | 明细与汇总同表 | 粒度不一致，聚合易重复计数 | P1 | 表内既有单笔字段又有 `total_*`/`sum_*` 且行含义混合 |

## C. 时间与审计

| # | 反模式 | 为什么坏 | 默认级 | 检测线索 |
|--:|--------|----------|:--:|----------|
| C1 | **金额/状态可改而无历史** | 事后无法归因、对账无依据 | **P0** | 主表有 `amount`/`status` 但无对应 `*_log`/`*_history`/事件表 |
| C2 | **软删破坏唯一约束** | 删后不能重建同名，或删后能建脏重复 | **P0** | 有 `deleted_at`/`is_deleted` 且唯一键未含它、也非部分索引 |
| C3 | 缺 `created_by`/`updated_by` | 只知何时改、不知谁改 | P1 | 有 `created_at` 无 `created_by` |
| C4 | 时区语义混乱 | 跨区业务时刻错位 | P1 | 同库混用 `datetime` 与 `timestamp(tz)` 存同类时刻 |
| C5 | 有效期需求用原地 update | 答不出「当时按哪个值」 | P1 | 价格/汇率/合同/配额表无 `valid_from`/`valid_to` |
| C6 | 无界增长表无归档策略 | 迟早拖垮备份与查询 | P1 | 日志/流水/消息表 + 无分区无清理任务 |

## D. 类型与精度

| # | 反模式 | 为什么坏 | 默认级 | 检测线索 |
|--:|--------|----------|:--:|----------|
| D1 | **浮点存金额** | 累加误差、对账不平 | **P0** | `rg -n -i '(float|double|real)' <真源>` 后看列名是否金额/计量 |
| D2 | 需查询字段塞进 JSON | 无类型无约束，查询只能全扫或函数索引 | P1 | JSON 列 + 代码里对该 JSON 键做 where/排序 |
| D3 | 原生 DB `ENUM` 承载可变值集 | 加一个值要 DDL，且不可移植 | P2 | `rg -n -i "enum\("` |
| D4 | 多布尔组合表达状态 | 存在非法组合，无法约束流转 | P1 | 同表 ≥3 个 `is_*` 且业务上互斥 |
| D5 | MySQL `utf8`（非 `utf8mb4`） | emoji/扩展汉字截断 | P1 | `rg -n 'utf8[^m]'` |
| D6 | 一律 `varchar(255)` / 一律 TEXT | 无业务约束；行外存储读放大 | P2 | 列宽高度一致或大量 TEXT |
| D7 | 敏感字段明文落库 | 合规风险 | P0/P1 按数据定 | 身份证/手机/密钥/口令列无加密或摘要说明 |

## E. 约束与并发

| # | 反模式 | 为什么坏 | 默认级 | 检测线索 |
|--:|--------|----------|:--:|----------|
| E1 | 关键列可空 + 应用层「保证」 | 脚本与并发会绕过 | P1 | 业务必需列 `NULL` 允许 |
| E2 | 哨兵值当空（`0`/`''`/`1970-01-01`/`-1`） | 污染聚合与判空 | P1 | `DEFAULT '0'`/`DEFAULT ''` 在语义为「未设置」的列 |
| E3 | 缺乐观锁/条件更新依据 | 库存与余额必然竞态 | **P0**（涉金额/库存） | 主表无 `version`，且代码为「查→算→写」 |
| E4 | 唯一约束漏租户前缀 | 跨租户冲突或越权 | **P0** | 多租库中 `UNIQUE(code)` 而非 `UNIQUE(tenant_id, code)` |
| E5 | 分库下无 FK 且无对账 | 孤儿数据长期积累 | P1 | 无 FK + 无孤儿清理/校验任务 |
| E6 | 业务表 `ON DELETE CASCADE` | 一次误删连锁清空 | P1 | `rg -n -i 'ON DELETE CASCADE'` |

## F. 演化与迁移

| # | 反模式 | 为什么坏 | 默认级 | 检测线索 |
|--:|--------|----------|:--:|----------|
| F1 | **无版本化 migrations**（运行时建表/手改库） | 环境漂移、不可重放、无回滚 | **P0** | 无 migrations 目录，或代码里 `AutoMigrate`/`create_all` 作为唯一真源 |
| F2 | **真源分裂**：migrations / DDL / ORM 三者不一致 | 谁是真的都说不清 | **P0** | 三处列集合比对不一致 |
| F3 | 破坏性变更无 expand/contract | 需停机，回滚要数据修复 | P0 | 迁移里直接 `DROP COLUMN`/`MODIFY` 关键列且无过渡版本 |
| F4 | 迁移无回滚（只有 up） | 出事只能硬扛 | P1 | 迁移文件缺 down/`-- rollback` 段 |
| F5 | 过早分片/分区且键选自非主访问路径 | 跨片查询 + 二次迁移 | P1 | 分片键与主要 where 条件不符 |
| F6 | 生产种子与演示种子混一 | demo 数据进生产 | P1 | seed 脚本无环境判别 |

## G. 访问路径

| # | 反模式 | 为什么坏 | 默认级 | 检测线索 |
|--:|--------|----------|:--:|----------|
| G1 | 主查询路径无匹配索引 | 全表扫，量一上来就崩 | P1（大表 P0） | 高频 where 列组合不在任何索引前缀 |
| G2 | 外键列无索引（PG） | 父表删改全表扫子表 | P1 | FK 列不在索引首位 |
| G3 | 冗余索引（`(a)` 被 `(a,b)` 包含） | 写放大、空间浪费 | P2 | 索引列表前缀包含关系 |
| G4 | 低选择性单列索引 | 优化器基本不用 | P2 | `is_*`/`status` 单列索引 |
| G5 | 大字段与热点列同表 | 扫描读放大 | P2 | TEXT/BLOB 与高频小列混存 |
| G6 | OLTP 主表跑报表聚合 | 拖慢事务 | P1 | 代码里对主表做无时间窗的全量聚合 |

## H. 语义漂移与代码替库兜底（S4 专属，只看 DDL 发现不了）

| # | 反模式 | 为什么坏 | 默认级 | 检测线索 |
|--:|--------|----------|:--:|----------|
| H1 | **代码手写防重，库无唯一约束** | 应用层挡不住并发、脚本、第二个服务；脏数据只是还没进来 | **P0** | 代码有「count/find 后再 insert」或 `FOR UPDATE` 防重，而该业务键无 `UNIQUE` |
| H2 | **状态机只活在代码里** | 库允许任意状态值与非法跳转；数据修复 SQL 一改就越轨 | P1（金额/审批相关 P0） | 代码有流转白名单或大 switch，库里 `status` 无 CHECK/无流转记录表 |
| H3 | JSON 键被 where/order/聚合 | 该字段本该是列；查询只能全扫或依赖函数索引 | P1 | `json_extract`/`->>`/`JSON_CONTAINS` 出现在查询条件 |
| H4 | **文档明确的业务约束未落库** | 规则写在纸上，库不设防 | **P0**（唯一性/精度/隔离）· P1（其它） | 文档抽出的规则 `enforced_in_db: no`（见 scan-workflow §2.1） |
| H5 | 枚举值域三方漂移 | 代码常量、字典表、库 CHECK 不一致；出现库里存在但代码不认的值 | P1 | 代码 `STATUS_*` 常量集合 ≠ 字典表行 ≠ CHECK 取值 |
| H6 | 同一概念多张表并存 | 双写不同步，报表口径打架 | P1 | 两表列集合高度重叠且分别被不同模块写入 |
| H7 | 文档字段含义与实际写入不符 | 下游按文档理解，取到的却是另一回事 | P1 | `docs/data` 说明 vs 代码实际赋值/单位/量纲不一致 |
| H8 | 代码绕过软删语义 | 部分查询漏 `deleted_at` 条件 → 已删数据复现 | P1 | 读该表的位置有的带软删条件、有的不带 |
| H9 | 库里有而代码从不读写的列/表 | 无人维护的僵尸结构，误导后来者，迁移时还要陪跑 | P2 | codegraph/rg 查无引用（须双工具确认再报） |
| H10 | 代码在应用层做跨表聚合以补模型缺失 | 说明缺读模型或缺关联表 | P2 | 多次查询后在内存 join/汇总的热路径 |

**H 组定级原则**：判断依据是「库不设防的后果」，不是「代码写得好不好」。代码兜底得再严密，
也挡不住并发、运维脚本与第二个消费者——所以 H1/H4 默认就是 P0。

## I. 迁移未收口与目标态漂移（ADR 定了、现网没跟上）

这组的共同特征：**问题不在任何单张表上，而在「同一件事有几条并行通路」**。逐表看每张都说得通，
连起来看才发现写入走哪条取决于入口，读出来的口径因此不一致。只做单表体检的评审必然漏掉这组。

| # | 反模式 | 为什么坏 | 默认级 | 检测线索 |
|--:|--------|----------|:--:|----------|
| I1 | **ADR/arch 已定目标态，现网仍跑旧路径** | 两套模型并存，新人不知该按哪套写；每个需求都要在两套上各改一遍 | **P0** | ADR 定的关系形状 ≠ 现网 DDL；迁移历史里有目标态的 expand 但无对应 contract |
| I2 | **同一关系存在多条并行通路**（直连 + 多态表 + 选择器） | 写入走哪条取决于入口；读时口径不一致；无法用约束保证一致 | **P0** | 两实体间既有直接外键、又有关联/多态表、又有「选择器」类间接表 |
| I3 | **expand 做了、switch 部分、contract 从未做** | 僵尸结构仍被写入，长期双写无人收口 | **P0**（仍被写入）· P1（只读） | 新旧列/表同时被写；迁移目录里有加无删；旧结构最近仍有写入代码 |
| I4 | 双写无收口计划 | 「以后再切」等于永不；技术债利息按需求数计息 | P1 | 有双写代码但无切换开关、无触发条件、无 plan/ADR 挂号 |
| I5 | **统一身份被多态表分叉** | 目标态本要共享同一主键作统一身份，多态表把身份拆成 `(type, id)` 二元组 → 无法外键、无法唯一、跨模块口径分裂 | **P0** | ADR 声称共享某表主键，实际存在 `*_type + *_id` 绑定表承载同一语义 |
| I6 | **「主绑」这类基数约束只靠代码维护** | `0..1` 主绑无唯一索引 → 并发下可出现两个主绑，且事后无法判定哪个为真 | **P0** | 文档写 `0..1`/「唯一主」，库里无部分唯一索引或等价约束 |
| I9 | **ADR 定的目标态本身违反建模底线** | 照它收口 = 用迁移成本把错误决策焊死；并存至少还留退路 | **P0**（阻断收口） | 用八维重打 ADR 定的形状，命中硬门槛或 A/B/D/E 组即 `adr_wrong`（如统一身份定成多态二元组、唯一主交给应用层、金额浮点） |
| I10 | **目标态被现网普遍绕开** | 通常说明目标态难落地，不是团队不自觉 | P1（证据用于给 ADR 定 verdict） | 新结构建了却无写入；为适配目标态写了大量转换层；写入仍走旧通路 |
| I8 | **多通路并存且无任何目标态定义**（没有 ADR/arch 钉死哪条合法） | 没有真源 → 谁都可以再加第四条通路；每个新需求都在加深分叉 | **P0** | 步 5 列出 ≥2 条通路，且 `docs/adr/`、`docs/arch.md`、`docs/data/` 均无相关约定 → 进 `mode=redesign` |
| I7 | 角色/关系被写成实体表 | 如把「执行者」建成独立表而目标态只要求它出现在任务队列中，多出一层无主的中间态 | P1 | 某表只承载一条关系且无自身属性与生命周期 |

**定级原则**：I 组按「并存持续多久 + 旧路径是否仍被写入」定级。仍在双写 → P0，因为每天都在生产新的
不一致数据；已停写只剩残留结构 → 降 P1/P2，按 contract 步清理。

**必须产出目标态对照**：命中 I 组时，报告要给「目标态 vs 现网」两张关系对照（可用 Mermaid 或表格），
并逐条标出差异属于 `未收口` / `已漂移` / `目标态本身需重开 ADR`。只写文字描述不算。

## 检测纪律

1. **命中 ≠ finding**：每条都要读真源确认，并写清「哪个业务操作会因此出错」。
2. **反模式编号进报告**：finding 带 `pattern: A1` 便于跨轮对比与去重。
3. **一处证据不够时标 unverified**：尤其 `blast_radius`（消费方数量）与量级判断。
4. **各组独立计数**：A–I 九组各自有 finding 计数器，避免全部堆在某一组造成「其它组没问题」的错觉。
   **H 组为空需要解释**：正常项目几乎总有代码替库兜底的地方；H 组交白卷通常意味着没读代码，
   须在报告写明实际读过哪些 DAO/Service 文件。
5. **勿把非问题当反模式**：见 SKILL.md「非问题」，特别是有意反范式、方言差异、字典小表缺索引。
