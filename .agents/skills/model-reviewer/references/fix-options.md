# 双修法 · 多维推荐 · 迁移剧本 · go-fast 交接

每条 finding 都要走完 §1→§2；破坏性变更再加 §3；用户确认后按 §4 交接。

---

## 1. 双修法（强制两案）

| 案 | 定义 | 常见形态 |
|----|------|----------|
| **`min_cost` 最小代价** | 不改既有列语义、不需大回填、可当周上线的止痛动作 | 加唯一/部分唯一索引；加 CHECK；加可空影子列并双写；加 `version` 列；加对账/孤儿清理任务；加归档任务；加缺失索引；应用层补校验 + 监控 |
| **`long_term` 长期最优** | 模型层面正确的形状，通常需迁移与灰度 | 提取实体成新表；改主键/唯一键；拆宽表；引入事件表或 SCD2 有效期；JSON 字段提列；状态多布尔收敛为状态机；分区/归档改造；类型改精度 |

**规则**

1. 两案都要写「做什么 + 影响哪些表/列 + 是否需要回填 + 是否需要改调用方」。
2. 两案相同时写 `long_term: same`，并说明**为什么没有更彻底的做法**（例如已是正确形状，只是缺一个约束）。
   不许用 `same` 偷懒回避思考。
3. `min_cost` 不得是「加个注释」「文档里写明」这类不改变系统行为的动作——那不叫修法，叫记债。
4. 若 `min_cost` 会**加大**将来迁移成本（例如为绕过唯一键冲突先塞一列脏标记），必须显式写出这笔利息，
   并在推荐里权衡。

## 2. 多维推荐（必须给推荐，且必须说明原因）

只摆两案让用户自己挑，等于把刚做完的扫描与影响面分析扔掉——用户不知道有多少代码在读这张表。
所以**必须选一个**并给理由。

### 2.1 六维论证（逐维给结论 + 依据，不适用写「不适用」及原因）

| 维度 | 要回答什么 |
|------|------------|
| **架构与边界** | 修在模型层还是靠应用层兜？会不会把业务规则永久留在代码里、让库继续允许脏数据 |
| **长期维护** | 下个相似需求来时是加列就行，还是又要一次迁移？债是收敛还是繁殖 |
| **可靠性与正确性** | 能否真正阻止脏数据/竞态/不可追溯，还是只降低概率；失败是否可见 |
| **迁移风险与回滚** | 是否锁表、要回填多少行、能否分批中断、回滚是 revert 还是数据修复；存量违规数据怎么处理 |
| **性能与容量** | 对写放大、索引体积、主查询路径的影响；三年量级下是否仍成立 |
| **合规与运维** | 审计/保留期/PII/加密要求；是否需要停机窗口与值班配合 |

再加一句**开发体验**（调用方要改多少处、是否需要同步改 API 契约）。

### 2.2 推荐取值与常见判据

| `recommend` | 什么时候选它 |
|-------------|--------------|
| `min_cost` | 长期形状收益有限，或该表即将下线/重构；止痛已能挡住脏数据 |
| `long_term` | 现在改最便宜（未上线 / 数据量小 / 正好在动这块）；或 min_cost 会积累利息 |
| **`min_cost_then_long_term`** | **模型层最常见的诚实答案**：先止血挡住脏数据，`long_term` 挂号进 plan/ADR 排期。正在跑的库不该为完美形状停机 |
| `needs_product_decision` | 业务规则本身未定（是否允许同名、金额如何取整、状态能否回退）。此时**不给推荐**，转 product-reviewer / grilling |

选 `min_cost_then_long_term` 时**必须**写清：触发升级的条件（量级阈值、下一个相关需求、某个里程碑）
与挂号位置（`docs/automate/plan.md` 条目或 ADR），否则「以后再说」等于永不。

### 2.3 还要写清三件事

1. **未选那案为什么不选**，以及它在什么条件下反而更优——只夸推荐项是推销不是建议。
2. **推荐的代价**：风险、回滚粒度、遗留债、需要的窗口与人力。没有代价的方案通常是没想清楚。
3. **置信度** `high | medium | low`。以下任一成立**不得**报 `high`：真源分裂未澄清、量级未知、
   `blast_radius` 为 `unverified`、目标引擎版本能力未验证、业务规则存疑。并写明缺哪条证据。

**禁止**：一律推荐最小改动以显得稳妥；一律推荐彻底重构以显得专业；用「建议优化表结构以提升性能」
这类无信息量的话。范围由证据定，不由姿态定。

## 2.4 特例：半迁移长期并存（I 组）的双修法形态

这类 finding 的两案与普通字段问题不同，容易写偏，固定为：

| 案 | 内容 |
|----|------|
| **`min_cost`** | **冻结旧通路的写入**（下线旧入口 / 加开关只读 / 加约束禁止新写）+ 存量不一致对账查询 + 挂号收口计划。目的是**先止住每天新增的不一致**，而不是立刻清理历史 |
| **`long_term`** | 完成 contract：把旧通路数据并入目标态结构 → 证明无引用 → 删除旧表/旧列；把目标态的基数契约（`0..1` 主绑、统一身份共享主键）落成真约束 |

**推荐几乎总是 `min_cost_then_long_term`**，理由：并存本身在持续生产脏数据，止血不能等；但清理历史
需要对账、需要窗口、且删除不可逆。**先冻结、后清理**是这类问题唯一稳的顺序。

两个必须写清的点：

1. **冻结顺序**：先冻写、再对账、最后删。反过来（先删后冻）会在删除期间继续有新写入落到旧结构。
2. **目标态是否仍成立**：若 ADR 已过时（业务变了），不要机械收口——标 `needs_product_decision`
   或建议重开 ADR。**收口到一个错误的目标态比并存更贵。**

## 3. 迁移剧本（破坏性变更必填）

模板，逐步填。缺任一步 → 该建议不得进推荐项。

```markdown
### 迁移剧本 M-<n>：<一句话目标>

- 目标引擎/版本：            # 决定可用手法
- 存量体量：                 # 行数量级 + 违规行数（先跑校验查询数出来）
- 锁风险：                   # 该 DDL 在该引擎该版本是 instant / inplace / rebuild；大表预估耗时

| 步 | 动作 | 可回滚点 | 验证 |
|----|------|----------|------|
| 1 expand | 加新列/新表；旧路径不变；必要时双写或触发器同步 | revert 该迁移（新结构未被读） | 新旧一致性抽查查询 |
| 2 backfill | 分批回填（批大小/限速/可中断/幂等） | 停止任务；新结构仍未被读 | 计数与抽样比对查询 |
| 3 switch | 读切新结构（可用开关灰度） | 关开关回切旧读 | 业务指标 + 错误率观察期 |
| 4 contract | 停写旧结构 → 删列/删表 | **此步之后不可逆** → 前置：备份 + 观察期已过 | 确认无代码引用（codegraph/rg 证据） |

- 存量违规数据处置：         # 清理/修正/隔离，谁审核
- 需要停机窗口：是/否        # 是则说明时长与业务影响
- 观察期：                   # switch 后多久才允许 contract
```

**纪律**：`contract` 与 `switch` **不得**在同一个发布里；回填任务必须幂等可重跑；
删除动作前必须有「无引用」的检索证据。

## 4. go-fast 交接（用户确认后）

改表属 `structural`，**不走无人值守**。确认后：

1. **Read** [go-fast](../../go-fast/SKILL.md)，按**路径 B**（本 skill 报告 ≠ 现成 Path A 规格）。
2. 报告即 `spec_ref`，go-fast 据此出 `docs/specs/model-<slug>.md`，至少含：
   - finding ID + 采纳的修法（`min_cost` / `long_term`）+ 为什么
   - **迁移剧本**（§3 表格原样带入）与回滚点
   - 可观察验收：迁移可从零顺序重放、回滚脚本已验、存量校验查询与期望结果、受影响接口回归
   - 非目标（不顺手重命名、不夹带无关索引调整、不改业务规则）
3. **ADR**：任何改键/改语义/拆表/分区改造**先落** `docs/adr/model-<slug>.md`（提议中 → 合回后已接受 + 补验证节）。
   缺 ADR 不得开工。
4. **切片纪律**：
   - 一张表族一片；**同一表结构禁止并发**（编排契约「不可同波」已含）
   - 有回填/双写的片 `attendance: attended`；纯新增可空列/加索引的低风险片可批量但仍需证据
   - 迁移与消费方代码同片（避免半截状态），或先合契约片再并行
5. **证据**：迁移前后各跑一次校验查询并留工件；`case-count` 不降；合回前 `gate-check batch`。
   命令见 [evidence.md](../../go-fast/references/evidence.md)。
6. **未做的 `long_term` 进 `remaining`** 并挂号（plan 条目或 ADR「已知延期」），不许悄悄消失。

**用户只选「最小代价止痛」时**：同样走 go-fast（要 migrations 与证据），但可合并为单片；
`long_term` 全部挂号。**不要**因为改动小就手改库。
