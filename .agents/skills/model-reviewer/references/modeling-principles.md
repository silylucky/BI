# 建模规范与设计原则（评审锚点真源）

八维（D1–D8）的子项、业内通行原则、以及「怎么算好/怎么算差」的打分锚点。
本文是**判断依据**，不是清单复读；报告里写结论与证据，不要把本文成段抄进去。

---

## 0. 三层建模与本 Skill 的落点

| 层 | 产物 | 谁负责 |
|----|------|--------|
| 概念模型 | 有哪些业务实体、实体间什么关系（ER 图，不含类型） | product-blueprint / create-evolution-arch |
| 逻辑模型 | 实体→表、属性→列、键与约束、范式取舍（与引擎无关） | **本 Skill 主战场** |
| 物理模型 | 引擎特性、索引、分区、存储参数、容量 | **本 Skill D8** + code-reviewer 性能 lane |

评审顺序**必须自上而下**：概念不对时优化索引是浪费。发现概念层缺实体（D1 P0）就先报它，
不要在错误的表上讨论字段类型。

---

### 0.1 为什么必须读代码与文档，而不只读 DDL

一份 DDL 只能告诉你「库里长什么样」，回答不了「这样对不对」。判断合理性需要两个外部参照：

1. **文档给「应然」**：业务要求什么唯一性、什么精度、什么状态流转、什么保留期。没有这个参照，
   评审就只能退化成套用范式与命名规范——那是查体例，不是查设计。
2. **代码给「实然」**：真实访问路径（决定索引是否合理）、真实值域（决定类型与枚举是否合理），
   以及最有价值的一类信号——**代码在替库做什么保护**。

第 2 条值得单独强调：当你看到代码里手写「先查一遍再插入」、`FOR UPDATE` 锁、或一个状态流转白名单，
那几乎总意味着**模型少了一个约束**。开发者已经用应用逻辑补上了库的缺口，于是缺口在 DDL 里看不见。
但应用层补丁挡不住并发、挡不住运维手工 SQL、挡不住第二个接入的服务——所以这类缺口是真实的 P0，
不是「已经处理了」。

反向也成立：库里有而代码从不读写的列与表，是无人维护的僵尸结构，会误导后来者并在每次迁移时陪跑。

## 1. D1 概念完整性与粒度

**原则**

1. **一表一事实**：一张表的每一行应回答同一个问题（「一个订单」「一次库存变动」）。混装即失去粒度一致性。
2. **生命周期一致**：同表列应有相近的变更频率与生存期。用户基本信息与用户最后登录时间混在一张宽表，
   会让高频写入拖累低频读取，且备份/归档策略无法分离。
3. **区分事实与状态**：「发生了什么」（不可变事件/流水）与「现在是什么」（可变状态）应分表。
   把两者混在一张表会导致要么丢历史，要么每次查现值都要聚合全量。
4. **区分事务与报表**：OLTP 主表不承载报表宽列。报表需求用读模型/物化视图/数仓解决（CQRS 思路）。
5. **实体缺失识别**：如果业务对话中反复出现某个名词，而库里没有对应表（它被塞成某表的几个列或
   JSON 里的键），通常就是缺实体。典型：地址、附件、审批、价格策略、配额。

**打分锚点**

| 分 | 表现 |
|----|------|
| 90+ | 表与业务实体一一对应，粒度一致，事件/状态分离，报表不侵入 OLTP |
| 80–89 | 个别表略宽或有轻微混装，但边界仍清楚 |
| 70–79 | 存在一张承载多概念的表，改动时反复牵连 |
| <70 | 上帝表 / 明细与汇总混存 / 关键实体缺失（用 JSON 或多列凑） |

## 2. D2 键与身份

**原则**

1. **主键必有且稳定**：主键值一旦分配不应改变。用会变的业务字段（手机号、邮箱、编码）作主键 → 改一次牵全库。
2. **代理键 + 自然键并存**：代理键（自增/雪花/ULID/UUID）做主键与外键引用；**自然键必须另建唯一约束**。
   这是最常被漏的一条——没有自然键唯一约束，重复业务数据一定会进来（并发下「先查后插」拦不住）。
3. **代理键选型**：
   - 自增整型：最小、索引最友好；缺点是暴露量级、分库需分段、跨库合并冲突。
   - **单调有序 ID**（雪花/ULID/UUIDv7）：分布式友好且保持 B+ 树顺序插入。
   - **随机 UUIDv4**：在聚簇索引引擎（MySQL InnoDB）上导致页分裂与写放大，大表慎用；PG 相对宽容但索引仍变大。
4. **复合主键的取舍**：关联表（M:N）用两外键复合主键是自然的；但若该关联本身会被其它表引用或需要独立属性，
   给它一个代理键更利于演化。
5. **幂等键**：对外接口的重试防重要有落库的幂等键（唯一约束），不能只靠应用内存或缓存。
6. **跨表引用类型一致**：`bigint` 引用 `int`、`varchar(32)` 引用 `char(36)` 会导致隐式转换与索引失效。

**打分锚点**：无自然键唯一约束或主键可变 → ≤40（命中硬门槛 2）。

## 3. D3 关系与基数

**原则**

1. **基数要在约束里，不只在文档里**：1:1 用唯一外键表达；1:N 的 N 侧持有外键；M:N 必须有关联表。
2. **可选性显式**：关系是否必需体现为外键列 NOT NULL 与否，不是靠代码判断。
3. **禁列表列**（jaywalking）：`tag_ids = "1,2,3"` 无法约束、无法索引、无法 join，改一次要扫全表字符串。
4. **多态外键谨慎**：`target_type + target_id` 无法用 FK 约束、无法保证引用存在。可接受的前提是
   有应用层强校验 + 孤儿清理任务；否则拆成多张关联表或用「超类型表」承载引用。
5. **EAV 只在真正开放式场景用**：用户自定义字段、产品可变规格。业务已知的属性一定要提成列——
   EAV 会让查询、类型、约束、报表全部退化。开放式需求的现代折中是 JSON 列 + 已知字段提列 + 生成列索引。
6. **自引用与树**：邻接表（`parent_id`）简单但深查递归；需要频繁查子树时考虑路径枚举（materialized path）
   或闭包表，选型写进 ADR。

## 4. D4 时间与审计

**原则**

1. **审计四列起步**：`created_at` / `created_by` / `updated_at` / `updated_by`。缺 `by` 时事后无法归因。
2. **时区**：存**时刻**用带时区语义的类型（PG `timestamptz`、MySQL `TIMESTAMP` 或统一 UTC 存 `DATETIME` 并
   全链路约定）。存**日历日**（生日、账期）用 `DATE`，不要塞时刻。混用是跨区业务的经典事故源。
3. **不可变优先**：金额、状态、权限这类会被追问「当时是多少」的数据，应有不可变记录：
   状态变更表 / 流水表 / 快照。只留当前值 = 放弃归因能力。
4. **双时态区分**（重要且常被忽略）：
   - **有效时间**（业务何时生效）：`valid_from` / `valid_to`，如价格、合同、汇率。
   - **系统时间**（记录何时写入）：`created_at`。
   报价单要回答「昨天下单时按哪个价」，只有 `updated_at` 是答不出来的 —— 这类维度要 SCD2
   （新增一行 + 关闭旧行的 `valid_to`），而不是原地 update。
5. **软删除**：`deleted_at` 时间戳优于 `is_deleted` 布尔（顺带记录时间）。**必须同时解决唯一约束**：
   - PG：部分唯一索引 `WHERE deleted_at IS NULL`（最干净）
   - MySQL：唯一键含 `deleted_at`（用 `0`/固定值代表未删），或改为归档表迁移
   两者都不做 → 命中硬门槛 3。
6. **归档与保留**：无界增长表（日志、流水、消息）要有保留期与归档/分区策略，写进模型文档。

## 5. D5 类型与精度

**原则**

1. **钱与计量禁二进制浮点**：`DECIMAL(p,s)` 或整型最小单位（分）。`FLOAT/DOUBLE/REAL` 存金额是硬门槛 1。
   同时约定舍入规则归属（DB 还是应用），避免两侧不一致。
2. **枚举承载**：
   - DB 原生 `ENUM`（MySQL）：改值要 DDL，演化成本高，跨引擎不可移植 → 一般不推荐。
   - **小整型 + 应用常量 + 字典表**：最灵活，需保证字典表与代码同源，且值有注释。
   - **短字符串 + CHECK**：可读性最好，加值改 CHECK（PG 便宜，MySQL 稍贵）。
   选型看「值集变更频率」和「是否需要用户可配」——用户可配的一定要落字典表。
3. **布尔 vs 状态机**：多个 `is_xxx` 布尔组合表达状态，容易出现非法组合（既已取消又已发货）。
   状态本身应是单列状态值 + 合法流转约束。
4. **JSON 列边界**：可以放「不参与查询与约束的附加信息」「真正不定形的外部载荷」。
   **不要**放需要被 where/join/排序/统计的字段——那说明它该是列（PG 可用生成列 + 表达式索引折中）。
   JSON 里的字段没有 NOT NULL、没有类型、没有默认值，等于放弃数据库的全部保护。
5. **长度与字符集**：`utf8mb4`（MySQL 的 `utf8` 存不了 emoji 与部分汉字扩展）；文本长度按业务上限设定，
   不要一律 `varchar(255)` 也不要一律 `TEXT`（行外存储影响读放大）。
6. **同义列一致**：同一概念在各表的类型/长度/字符集/排序规则必须一致，否则 join 隐式转换、索引失效。
7. **敏感字段**：PII 要标记；需加密落库的（身份证、手机号、密钥）明确算法与密钥来源；
   本体系默认国密场景用 SM4 落库、SM3 摘要（见 create-project-rules 红线），并保留可检索需求的处理方式
   （盲索引/摘要列），不要加密完又要求模糊查询。

## 6. D6 约束与完整性

**原则**

1. **约束在库里才叫约束**：应用层校验会被绕过（脚本、运维手工、并发、第二个服务）。
   能落 NOT NULL / UNIQUE / CHECK / FK 的就落。
2. **默认值与空语义**：区分「不知道」（NULL）与「没有」（空串/0）。用 `0`、`''`、`1970-01-01`、`-1`
   当哨兵值会污染聚合与判空逻辑。
3. **FK 落不落**：单库优先落（能挡孤儿、能表达基数）。分库分表/超高写入场景可不落，但**必须**有
   应用层校验 + 定期孤儿对账任务，否则报 P1。
4. **级联谨慎**：`ON DELETE CASCADE` 在业务表上易造成意外批量删除；金融/审计类数据用 `RESTRICT` + 软删。
5. **并发正确性属于模型**：库存扣减、余额变更、状态流转要靠**唯一约束 / 乐观锁 `version` / 条件更新
   `WHERE status = 期望值`** 保证，而不是先查后写。模型里没有 `version` 或没有可用的条件列，
   代码就只能写出竞态——这属于 D6 finding，不是 code-reviewer 的。
6. **唯一约束要贴业务**：「同一租户下编码唯一」是 `(tenant_id, code)`，不是 `code`。多租户尤其常错。

## 7. D7 演化与扩展性（本 Skill 的重心）

好模型的判据不是现在多漂亮，而是**变化时改动是否局部、是否可回滚、是否无需停机**。

**原则**

1. **加列优于改列，加表优于加宽**：新增可空列几乎零成本；改类型/改语义/改非空要回填与锁。
   设计时给「一定会来的变化」留出加表位置（如价格→价格策略表）。
2. **扩展点设计**：预期用户可配的部分，选定一种扩展机制并写进 ADR：JSON 附加列（读多写少、不查询）、
   字典 + 关联表（需约束与统计）、EAV（真正开放）。**忌**三种混用。
3. **不要为想象中的规模预分片**：分表/分区键选错比不分更贵（跨片查询、二次迁移）。
   分片键必须来自**主要访问路径**（多租户→租户；订单→用户或时间；日志→时间）。
   未达量级时先做好单表 + 归档，把分片方案写进 ADR 待触发。
4. **破坏性变更四步法（expand / contract）**——本体系的标准剧本：
   1. **expand**：加新结构（新列/新表），双写或触发器同步，旧读路径不变
   2. **backfill**：分批回填存量（限速、可中断、幂等、可校验）
   3. **switch**：读切到新结构，观察期内可回切
   4. **contract**：停写旧结构 → 删除
   每步一个可回滚提交；跨步之间可发布。**没有这四步的「直接改」在生产库上不可接受。**
5. **在线 DDL 与锁**：MySQL 5.7/8.0 的 instant/inplace 支持范围、TiDB 的异步变更、PG 的
   `ADD COLUMN` 默认值优化与 `CREATE INDEX CONCURRENTLY`——评审时按引擎注明该动作是否锁表、
   大表预计耗时。大表加非空默认列、改列类型、加 FK 通常是锁风险点。
6. **migrations 纪律**：每次结构变更一个版本化迁移；可从零顺序重放；破坏性步骤有对应回滚；
   禁止运行时自动建表冒充迁移，禁止手改生产库（命中硬门槛 6）。
7. **多租户前瞻**：共享表 + `tenant_id`（最常见）要求**所有**唯一约束与主要索引以租户列为前缀，
   且查询强制带租户条件（最好在 DAO 层统一注入）。缺前缀既有越权风险也有性能悬崖。

## 8. D8 访问路径与容量

**原则**

1. **索引服务于查询，不是装饰**：先列出主要访问路径（按什么查、按什么排、按什么聚合），再看索引是否匹配。
   报告里应能给出「路径 → 索引 → 是否覆盖」的对照。
2. **复合索引最左前缀**：`(a,b)` 能服务 `a` 与 `a,b`，不服务单独 `b`。等值列在前、范围列在后。
3. **外键列必须有索引**（MySQL 自动建，PG 不自动）：否则父表删改会全表扫子表。
4. **覆盖索引与回表**：高频只读少量列的查询可用覆盖索引；但索引不是越多越好——写放大、
   冗余索引（`(a)` 被 `(a,b)` 包含）应清理。
5. **低选择性列单独索引无意义**（性别、是否删除），除非作为复合索引前缀或 PG 部分索引条件。
6. **行宽与大字段**：大 TEXT/BLOB 与热点小列同表会拖慢扫描（PG TOAST 稍缓解），考虑垂直拆分。
7. **容量与生命周期**：估算日增与三年后的行数量级。无界增长表必须有分区/归档/清理方案，
   否则「现在很快」只是还没到时候。
8. **统计口径**：报表聚合不要在 OLTP 主表上跑全量；预聚合表/物化视图/数仓分层。

## 9. 评分权重（八维加权）

| 维 | 权重 | 理由 |
|----|------|------|
| D2 键与身份 | 18% | 错了最贵，几乎必然二次迁移 |
| D7 演化与扩展性 | 18% | 本 Skill 的核心目标 |
| D6 约束与完整性 | 15% | 直接决定脏数据能否进来 |
| D1 概念完整性 | 14% | 决定后续所有讨论是否在正确的表上 |
| D4 时间与审计 | 13% | 缺失后不可追溯、不可补 |
| D5 类型与精度 | 10% | 金额精度是硬门槛，其余多可渐进 |
| D3 关系与基数 | 7% | 多数可通过加关联表渐进修 |
| D8 访问路径与容量 | 5% | 最可后补（加索引通常可逆） |

**总分 = Σ(维分 × 权重)**，四舍五入取整。命中任一硬门槛 → 总分上限 69（公共口径 §3）。
权重反映的是**可逆性**：越难回滚的维权重越高。这也是为什么「加索引」不能刷高总分。

## 10. 引擎差异速查（影响修法可行性，不作为 finding）

| 能力 | MySQL 8 / TiDB | PostgreSQL | SQLite |
|------|----------------|------------|--------|
| 部分唯一索引（软删友好） | 不支持（用唯一键含删除标记，或函数索引变通） | **支持** `WHERE deleted_at IS NULL` | 支持 |
| CHECK 约束 | 8.0 起支持 | 支持 | 支持 |
| 在线加列 | 多数 instant | 加可空列快；加默认值 11+ 优化 | 有限 |
| 在线建索引 | inplace | `CONCURRENTLY` | 需重建 |
| 改列类型 | 常需 rebuild | 常需 rewrite（部分兼容类型免） | 需重建表 |
| 原生 ENUM | 有（不推荐） | 有（改值需 DDL） | 无 |
| JSON 索引 | 生成列 + 索引 | GIN / 表达式索引 | 有限 |
| 分区 | 支持 | 声明式分区 | 无 |

评审建议必须落在**目标引擎实际支持的手法**上；不确定就写「需在目标版本验证」，不要给出跑不通的方案。
