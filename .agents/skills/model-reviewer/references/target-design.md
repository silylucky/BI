# 目标态设计与业务改造方案（`mode=redesign`）

用于**没有 ADR/目标态可依**，或**原有 ADR 经复核判为 `adr_outdated` / `adr_wrong`**（见 SKILL.md「ADR 复核」）、
现状就是一团并行通路的情况：把散落 finding 收敛成**一张目标模型**
加**一份业务改造方案**，并补出本该早就存在的 ADR。

与默认 `mode=review` 的区别：review 逐条出 finding + 双修法；redesign 多一步**综合**——
回答「那到底该长什么样、怎么一步步搬过去」。

**铁律：顺序不能颠倒。** 先定唯一身份 → 再定唯一合法通路 → 再落约束 → 最后才谈索引与性能。
颠倒过来（先优化索引、先加约束）会在错误的形状上做功，改完还要再改一次。

---

## 前置：不许自造业务语义

设计目标态需要知道业务真实意图，而现状代码只能告诉你「现在怎么跑」，说不清「本该怎样」。所以：

| 允许推断 | 必须问用户（进硬决策清单） |
|----------|---------------------------|
| 从代码用法归纳事实（谁写、写什么、并发怎么防） | 两条通路语义是否**本来就该不同**，还是历史重复 |
| 从数据分布归纳基数（是否真的 0..1） | 「主绑」到底唯一还是可多条；冲突时谁优先 |
| 从命名与引用方向归纳身份归属 | 某实体是**独立实体**还是**关系的一个角色** |
| 从查询归纳访问路径 | 是否允许有损合并（丢弃某通路独有字段） |

**硬决策清单 ≤5 条**，每条给推荐选项 + 理由，一次问完。超过 5 条说明范围太大，应先缩小到一个实体族。
业务规则完全不明的部分标 `needs_product_decision`，不要替产品定。

---

## S1 · 收敛事实（先把现状写清，再谈应然）

产出三张表，全部要有代码/DDL 出处：

**实体与通路清单**

| 实体对 | 通路 | 承载结构 | 谁在写（文件:行） | 该通路独有字段 | 最近是否仍写入 |
|--------|------|----------|------------------|----------------|----------------|

**通路语义差异**（决定能否合并的关键，最容易被跳过）

| 通路 | 在什么业务场景被写 | 表达的语义 | 与其它通路重叠部分 | 冲突时现状按谁 |
|------|-------------------|-----------|-------------------|----------------|

**存量数据体检**（合并方案要靠它定可行性）

```sql
-- 各通路各有多少行、多少重叠、多少冲突（按实际表名改写）
SELECT COUNT(*) FROM <通路A>;
SELECT COUNT(*) FROM <通路B>;
-- 同一对实体在两条通路都有记录且值不一致的数量 → 决定是否需要人工裁定
```

冲突行数为 0 → 合并是机械动作；冲突行数大 → 必须先定裁定规则并可能需要业务确认，写进硬决策。

## S2 · 定唯一身份（identity）

多通路乱局的根源通常在这里：同一个东西有两种身份表示法。

| 候选 | 何时选 | 代价 |
|------|--------|------|
| **共享单一主键**（各视角共用同一张主体表的 id） | 各视角说的确实是同一个东西；需要跨视角外键与唯一约束 | 主体表成为热点；需先统一存量 id |
| 二元组 `(type, id)` 多态身份 | 被引用方**确实**是异构且无共同主体表 | 无法外键、无法唯一、跨模块口径易分裂 —— 除非不得已，否则不选 |
| 超类型表 + 各子类型表 | 异构但有共同属性与共同引用需求 | 多一次 join；但恢复了外键与唯一性 |

**判据**：如果代码里存在「按 type 分支去不同表查同一件事」的逻辑，且这些表有共同的引用需求
（都要被绑定、都要被采集、都要出现在同一列表里）→ 该走**共享主键或超类型表**，不该是多态二元组。

结论写成一句：**「本域的统一身份是 `<表>.<列>`，所有关系一律引用它。」**

## S3 · 定唯一合法通路

原则：**两个实体之间只允许一条写通路。** 需要区分种类时用「类型化的单一关联表」，不是多张并行表。

| 目标形态 | 适用 | 长这样 |
|----------|------|--------|
| 直接外键 | 1:N 且无关联属性 | 子表持有 `parent_id` |
| **单一关联表** | M:N，或关联本身有属性（生效时间、是否主、操作人） | `a_id + b_id + 关联属性`，`UNIQUE(a_id, b_id)` |
| **类型化单一关联表** | 存在多种绑定语义（原来靠多张表区分） | 上表加 `relation_type` + `UNIQUE(a_id, b_id, relation_type)`，取值落 CHECK 或字典 |
| 超类型表 + 关联 | 被绑定方异构 | 关联只引用超类型表主键 |

**「选择器」类间接表**（把筛选条件存成表以动态选出目标）几乎总应降级为：
关联表里的**物化结果** + 选择规则单独存（规则是配置，结果才是关系）。
把「规则」与「关系」混在一张表里，导致既不能约束也不能审计。

**角色 vs 实体的判定**：某结构只承载一条关系、无自身属性与生命周期 → 它是**角色**，
应是关联表的一列（如任务的执行者），不该独立成表。

## S4 · 落约束（把业务规则从代码搬进库）

逐条把 S1 的语义差异与业务规则落成真约束：

| 规则 | 落法 |
|------|------|
| 关联唯一 | `UNIQUE(a_id, b_id[, relation_type])` |
| **`0..1` 唯一主**（主绑/默认项） | PG：`CREATE UNIQUE INDEX ... ON t(a_id) WHERE is_primary AND deleted_at IS NULL`；MySQL：唯一键含 `is_primary` 的稀疏表达或独立「主绑」表 `UNIQUE(a_id)` |
| 引用必须存在 | FK（单库）或应用校验 + 孤儿对账任务（分库） |
| 状态合法流转 | 状态列 CHECK + 流转记录表；禁止只在代码里 |
| 软删不破唯一 | 部分唯一索引，或唯一键含删除标记 |
| 租户隔离 | 所有唯一键与主索引以租户列为前缀 |
| 审计 | `created_at/by`、`updated_at/by`；关键关系变更进历史表 |

## S5 · 目标 DDL 草案

给出可评审的 DDL（不执行），每张表含：主键、唯一约束、外键、NOT NULL、CHECK、审计列、租户前缀、
必要索引（按 S1 的真实访问路径，不是凭感觉）。并标注：

- 与现状的对应关系（新表由哪些旧表合并而来）
- **有损点**：哪些旧字段在目标态无处安放 → 必须在硬决策里问，或保留为附加信息
- 命名与现有惯例一致（不顺手重命名无关表）

---

## S6 · 业务改造方案（模型改完，业务怎么跟上）

这是用户真正要执行的部分，缺任一节视为方案不完整：

| 节 | 必须写 |
|----|--------|
| **入口收敛** | 现有写入口逐个列出（API/后台/定时任务/脚本/数据修复）→ 保留哪个、下线哪个、谁改 |
| **写路径统一** | 统一后的唯一写入函数/服务方法；旧写入点如何改造或删除 |
| **读兼容** | 旧读法在过渡期怎么继续工作（视图 / 兼容查询 / 适配层），何时撤除 |
| **数据合并规则** | 逐通路映射到目标结构；**冲突裁定规则**（按时间最新 / 按来源优先级 / 人工核对）+ 谁审核 |
| **波次** | 按实体族切片；每片独立可发布可回滚；标明依赖顺序（先统一身份，再合并关系，最后删旧） |
| **对外契约影响** | API 字段/枚举/ID 语义是否变化；是否需要版本化或客户端同步 |
| **验收** | 每波的可观察验收：存量校验查询与期望值、并发防重实测、原有业务回归清单 |
| **回滚** | 每波回滚点；哪一步之后不可逆（删除步），前置条件（备份 + 观察期） |
| **风险与窗口** | 锁风险、是否需停机、观察期时长、值班安排 |

迁移四步（expand→backfill→switch→contract）与每步回滚点按
[fix-options.md](fix-options.md) §3 模板填；**`switch` 与 `contract` 不得同发布**。

## S7 · ADR 草稿（因为原来没有）

写 `docs/adr/model-<域>.md`（状态「提议中」），最小内容：

| 节 | 写什么 |
|----|--------|
| 上下文 | 现状几条并行通路 + 各自出处 + 已产生的具体问题（脏数据/口径不一致/改一个需求要改几处） |
| 决策 | 统一身份是什么；唯一合法通路是什么；关键约束清单 |
| **不做什么** | 明确不改的对外契约、不合并的语义、本次不动的表 |
| 后果 | 正面 + 负面 + 回滚点 |
| 备选与否决理由 | 至少一个被否方案及原因（例如「保留多态表」为何不选） |
| 验证 | 存量校验查询、并发实测、`gate-check` run_id（合回后补） |

**ADR 先落盘再开工**；合回后状态改「已接受」并补验证节。

**若是替换一份被判 `adr_outdated` / `adr_wrong` 的旧 ADR**：新 ADR 必须写清「取代 ADR-<n>」，
在「备选与否决理由」里写**旧决策错在哪 / 哪个前提已变**，并把旧 ADR 状态标为 `superseded`。
不要悄悄写一份新的把旧的留在原地——两份并存的 ADR 会让下一个人重演同样的困惑。

---

## S8 · 交付与确认

报告里按序给：现状通路图 → 目标态图 → 目标 DDL 草案 → 业务改造方案 → ADR 草稿 → **硬决策清单**。
两张图用 Mermaid，能一眼看出「多条 → 一条」。

停问：

> ①先冻结旧通路写入止血（不动结构）②按目标态执行改造（含数据合并，需窗口）③只要方案不动库
> ④目标态需要调整（我来说明业务差异）

**禁止**：目标态里塞用户没要求的新能力；把三条通路机械合并成一条却不处理语义差异（会静默丢信息）；
在硬决策未回答前就出「最终」DDL——未定项必须显式标 `待确认`。
