# 扫仓工作流（需求 × 代码）

目标：每条需求的匹配态都有**可复核证据**，不是凭印象打分。

## 0. 输入归一

- 招标 PDF/Word：抽取条款表；保留章节号。  
- Excel/表格：以行为 `REQ-ID`（无 ID 则自编 `REQ-001…` 并映射原行号）。  
- 聊天粘贴：先整理成条目表再扫仓。  
- 中英混排：术语表（甲方用词 → 仓内模块名）单列维护，避免漏搜。

## 1. 建搜索锚点图（一次）

| 层 | 搜什么 | 典型位置 |
|----|--------|----------|
| 产品表面 | 路由、菜单、页面标题 | `routes`、`*nav*`、`pages/`、`views/` |
| API | 路径、RPC、OpenAPI | `api/`、`handler`、`controller`、`proto` |
| 领域 | 实体、状态机、用例名 | `internal/`、`domain/`、`service/` |
| 集成 | 厂商/协议名 | `adapter`、`client`、`oauth`、`ldap`… |
| 安全 | 鉴权、RBAC、审计 | `auth`、`middleware`、`audit` |
| 部署 | 安装与运行 | `deploy/`、`helm/`、`compose`、`docs/service` |
| 文档 | 已声称能力 | `docs/**`、`README*`、`docs/ui` |

有 codegraph 且项目已索引 → 优先按符号探索；否则 Grep/Glob。**不要**全仓无目的通读。

## 2. 逐条（或按域批量）匹配

对每条需求：

1. 从条款提取 **3～7 个检索词**（业务名 + 可能的英文模块名）。  
2. 先文档后代码（或相反）：文档宣称 `FULL` 必须用代码复核。  
3. 命中后打开**入口到持久化/外部调用**的最短路径，判断能否真完成，而非仅有函数名。  
4. 判定匹配态（见主 Skill 表）；填写：

```text
REQ-ID | 态 | 锚点(路径:符号/路由) | 可演示？Y/N/Partial | 缺口一句话
```

5. 未命中：记录已搜关键词与目录范围 → 才可标 `MISSING`（或证据不足 → `UNKNOWN`）。

## 3. 域级加速（条目 >40）

1. 按主题聚类（认证、审计、资源管理、报表、集成…）。  
2. 每域选 **代表性必须项** 深挖路径；同构评分项可类推但抽检 ≥1 条。  
3. 报告中声明：**深挖集**与**类推集**，类推置信更低。

## 4. 特殊条款

| 条款类型 | 做法 |
|----------|------|
| 性能/容量数字 | 找压测报告或配置上限；无则 `PARTIAL/UNKNOWN`，勿用代码存在冒充达标 |
| 等保/资质 | 只认证书/报告/明确工程控制点；口头「支持」→ 非 FULL |
| 国产化/信创 | 查部署与依赖声明；运行时未验证 → 条件声称 |
| 「支持二次开发」 | 查 API/插件/扩展点文档与真实 SDK；仅开源仓 ≠ 满足 |
| 纯商务/服务响应 | 标 `N/A`（产品仓无法证明）或转用户提供运维承诺 |

## 5. 假绿探针（抽样）

对拟标 `FULL` 的必须项抽 ≥3 条做假绿探针：

- 是否 `ForceStub` / `TODO` / 固定成功返回？  
- 前端是否写死列表？  
- 集成是否未配置也可「成功」？  

命中 → 降为 `PARTIAL` 或触发硬门槛，并建议 [code-reviewer](../../code-reviewer/SKILL.md)。

## 6. 缺口方案最小集（MISSING / PROXY）

每条（或每簇）缺口写：

| 字段 | 内容 |
|------|------|
| 目标行为 | 用户/评测可见结果 |
| 真实验收 | 环境、数据、步骤（禁 mock 完成定义） |
| 落点 | 模块/服务/前端表面 |
| 依赖 | 外部系统 / 是否需 integration-research |
| 不做 | 明确非目标，防范围膨胀 |
| 切片 | 可独立验收的第一刀 |

## 7. 写入检查（报告前）

- [ ] 每条必须项有态 + 证据或「已搜无」说明  
- [ ] 无无锚点 `FULL`  
- [ ] 八维各有证据句  
- [ ] 硬门槛已检查  
- [ ] 应标口径与矩阵一致（不声称矩阵未支持的能力）  
- [ ] 未改业务代码（除非用户本轮明确要求实现）
