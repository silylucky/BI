# 自动发现：核心场景怎么选

仅 **自动模式** 使用。指定模式跳过本文的「打分入选」，只允许把发现结果放进 `optional.md` 附录。

## 输入源（按优先级读）

| 优先级 | 源 | 取什么 |
|--------|-----|--------|
| 1 | 用户/README/对外 docs「已支持」清单 | 宣称已交付的能力 = 默认 P0/P1 候选 |
| 2 | `docs/domain/*/md` 的 **Process Test Pack** | PT 场景直接映射为走查场景（改写为 UI 步骤） |
| 3 | 侧栏/顶栏菜单配置 | 一级业务入口；每个主域至少考虑 1 条主路径 |
| 4 | 前端路由表 | 补菜单未挂但已宣称的深链 |
| 5 | `docs/ui` 关键流 | 已文档化的关键流 |
| 6 | 领域包状态机 / 主 use-case 名 | 推断闭环（创建→提交→完成） |

无 docs 时：用 1+3+4，步骤触点从页面组件抄菜单文案与主按钮。

## 什么算「核心」（入 critical.md）

| 纳入 | 例子 |
|------|------|
| 登录 + 壳可用 | 任何 Console/Admin |
| 宣称已交付的主业务闭环 | 下单、创建资源、跑任务、审批通过 |
| 高风险但常用 | 权限拒绝是否诚实、主列表空态是否可行动 |
| 多角色关键差异（若 `.dev.roles`>1） | 低权看不到删除 |

| 不纳入主剧本（可进 optional） | 例子 |
|------------------------------|------|
| 每个列表页的完整 CRUD 地毯 | 交给 browser-reviewer 通用幕 W3 或 optional |
| 设置页文案/主题微调 | P2 |
| Storybook / 回调 / 纯 redirect | 排除 |
| README 写「即将推出」 | `blocked` 或不写 |

## 打分（粗排）

每条候选场景：

| 因子 | 分 |
|------|-----|
| README/对外宣称已支持 | +3 |
| 有 domain PT / 状态机主路径 | +3 |
| 一级菜单入口 | +2 |
| 含写操作主路径 | +2 |
| 仅详情只读浏览 | +1 |
| stub / mock 文档标明假能力 | −5（改 blocked 或剔除） |

主剧本取分数最高的 **3～8** 条（另加强制 S0 预检登录）。同域多条高度相似 → 合并为一条「代表路径」。

## 从 PT / 领域流程 → UI 步骤

1. 读 PT 的 Given / 步骤 / 期望 / API ID  
2. 映射到菜单与页面：用路由表、菜单文案、页头 CTA  
3. API 只写在「关联」；**走查步骤必须是 UI 操作**（除非产品无 UI 仅 API——则本 Skill 产出 API 检查清单并声明「不交 browser-reviewer，交 Postman」）  
4. 夹具写清：用现有数据 / 需先造数（造数若需写 API 且 allow_writes=false → `blocked` 或 `needs_confirm`）

## 指定模式附录

用户指定流程写完后，若自动扫描仍发现更高分未覆盖场景，写入 `optional.md`：

```markdown
## 建议增补（未纳入本次主剧本）

| 场景 | 理由 | 建议优先级 |
|------|------|------------|
| … | 宣称已支持但未在指定范围 | P1 |
```

禁止在未询问时把这些合并进 `critical.md`。
