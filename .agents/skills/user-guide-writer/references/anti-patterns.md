# 用户帮助反模式（以「批量生成帮助」为戒）

命中即不合格；改写时优先消灭这些，而不是润色同构骨架。

## 1. 模板复读（最伤信任）

| 反模式 | 用户感受 | 正确做法 |
|--------|----------|----------|
| 每篇相同的「前置条件：已登录（有效 session）+ 具备所需权限」 | 没人读；且常与正文矛盾 | 只写**本稿真需要**的前置；权限写具体名 |
| 每篇相同的「401 / 403 / 页面无入口」三段 | 排障区变噪音 | 全局问题单列一文并链接；本稿只留特有失败 |
| 除 title 外章节标题、句式、长度高度雷同 | 「机器说明书」 | 按文型重写；允许短文，允许删节 |

**自检**：任抽 3 篇，若「常见失败」可无损对调 → 整批重写。

## 2. 文型用错

| 反模式 | 正确 |
|--------|------|
| 概念文写成「逐步操作：1.记住组织 2.记住项目」 | Concept：定义、关系、边界、下一步任务链接 |
| 任务文只有功能介绍无步骤 | How-to：可执行步骤 + 成功确认 |
| 登录/会话文却要求「已登录」才可读 | 前置与目标一致 |

## 3. 实现细节外泄

| 反模式 | 放到哪 |
|--------|--------|
| 新手文强调 Cookie 名、HttpOnly、`redirect` 参数 | 删；或开发者参考文 |
| 成功标准写成 `URL 形如 /projects/{id}/…` 当主句 | 改成用户可见结果；路径作补充一行即可 |
| 错误码当标题（无症状描述） | 「登录后又跳回登录页」+ 处理 |

## 4. 步骤不可执行

| 反模式 | 正确 |
|--------|------|
| 「项目侧栏进入仓库/代码列表」 | 「在左侧导航点击 **代码** → **仓库**」（与 UI 一致） |
| 「或以 UI 为准」「或对应列表」 | 核对后写死文案；多名称时写「界面可能显示 A 或 B（部署差异）」并说明如何辨认 |
| 一步内完成进入+筛选+打开+编辑 | 拆步；每步一个动作 |
| 「编辑阶段/作业（或 YAML/编排器，以 UI 为准）」 | 先写主路径 UI；YAML 高级路径另步或另文 |

## 5. 导航与关联差

| 反模式 | 正确 |
|--------|------|
| `[concepts](/help/…)` `[pipe-author](…)` | `[核心概念：组织 / 项目 / 仓库](…)` |
| 相关链接堆 slug，无阅读顺序 | 「下一步」「相关任务」「深入」分组 |
| 欢迎页步骤是「打开帮助再选首次上手」循环 | 欢迎页讲价值与分册地图，上手步骤链到真正任务文 |

## 6. 语气与信息味道

| 反模式 | 正确 |
|--------|------|
| 像工单字段：适用角色/前置/逐步/预期/失败 | 可以保留结构，但**内容要像教人**，不像填表 |
| summary 复读 title | summary 写收益或场景（「三分钟建好第一个项目」） |
| 「所有新用户」+ 超管才能做的步骤 | 角色与步骤匹配；否则拆文 |

## 7. 改写策略（面对已有同构库）

1. 建**文型矩阵**（每 slug → concept/how-to/reference/troubleshoot）。  
2. 抽出真正共享篇：`登录与会话`、`权限与角色`、`找不到菜单时`。  
3. 其余篇删除复制的失败段与假前置，按 UI 重写步骤。  
4. 概念篇去掉逐步操作编号。  
5. 全库链接文字改成可读标题。  
6. 用 checklist 抽检 20% 篇；不过则继续改，禁止「只改 frontmatter」。
